# `zhiguang-go` 项目带读

> 这不是一份功能清单式文档，而是一份面向技术面试复盘的项目带读。
> 重点不在“这个项目有多少服务”，而在“面对公共内容场景，我是如何做业务建模、同步异步拆分、缓存设计和一致性取舍的”。

## 1. 项目定位与一期边界

### 1.1 一句话定位

`zhiguang-go` 是一个面向“公共知识广场”场景的内容平台后端，一期优先打通“发帖发布 -> 搜索索引 -> 公共 feed -> 点赞收藏回流”这条主链路。

这个定位很关键，因为它直接决定了后面的架构取舍：

- 它不是一个强社交导向的复杂时间线系统。
- 它不是先做关注推拉模型，再反过来适配公共内容。
- 它一期最核心的目标，是先验证内容生产、内容曝光、内容检索、内容互动这条闭环。

### 1.2 一期明确要做什么

一期围绕内容闭环，重点做四件事：

1. 用户可以先创建草稿，再补齐正文内容和元数据，最后发布。
2. 已发布且公开的内容，可以进入公共 feed，被其他用户浏览。
3. 已发布且公开的内容，可以进入搜索索引，被关键词检索。
4. 用户可以点赞、收藏，系统能够高吞吐地维护互动状态和计数展示。

### 1.3 一期明确不做什么

一期刻意不做以下能力：

- 不做关注时间线推拉模型。
- 不做复杂个性化推荐分发。
- 不追求所有派生视图都实时强一致。

这不是“漏做”，而是主动做减法。

如果一期同时做公共广场、关注时间线、个性化推荐，那么内容系统、社交关系系统、分发系统会耦合得非常重，复杂度会过早爆炸。当前阶段更合理的做法，是先把“公共内容广场”跑通，让系统先具备稳定的内容生产和消费闭环。

## 2. 系统整体架构

### 2.1 架构核心思想

这个项目最重要的架构思想，不是“微服务拆得多细”，而是下面这句话：

> 主业务事实走同步提交，搜索索引、缓存页、聚合计数、镜像表等派生视图走异步扩散。

也就是说，我会先判断一类数据到底是：

- 业务真相
- 还是为了读性能、检索能力、分页能力做出来的投影

只有真相层，才要求在关键路径里被强一致维护；投影层则允许最终一致，但必须做到可恢复、可重建、可对账。

### 2.2 核心组件划分

围绕主链路，当前最重要的组件有：

- `gateway`
  - 统一外部 HTTP 入口，负责把外部流量收口。
- `knowpost-rpc`
  - 内容主服务，负责草稿、正文确认、发布、详情、公共 feed。
- `search-indexer` + `search-rpc`
  - 前者消费 outbox 事件构建 ES 索引，后者提供搜索查询能力。
- `counter-rpc` + `aggregator` + `reconciler`
  - 负责点赞收藏状态、总数聚合、读模型恢复与定时对账。
- `user-rpc`
  - 用户与认证。
- `relation-rpc` + `syncer`
  - 负责关注主事实和关注镜像视图。
- `storage-rpc`
  - 负责 OSS 预签名上传能力。

### 2.3 主航道的高层数据流

主航道可以抽象成下面这张图：

```text
用户
  |
  v
gateway
  |
  v
knowpost-rpc ----------------------> MySQL(know_posts/outbox)
  |                                         |
  |                                         v
  |                                   Canal / Kafka
  |                                         |
  |                                         v
  |                                  search-indexer ------> Elasticsearch
  |
  +-------------------------------> Redis(feed cache / detail cache)
  |
  +-------------------------------> counter-rpc -> bitmap -> kafka -> agg -> sds
```

这张图要传达的核心不是组件名字，而是两件事：

- 内容发布的事实来源是 MySQL 主表。
- 搜索、缓存、计数都不是事实源，而是围绕事实源扩散出来的读模型。

## 3. 关键业务逻辑设计

### 3.1 发帖发布主链路

### 3.1.1 为什么要拆成“草稿 -> 正文确认 -> 发布”

内容创建不是一次性完成的，而是拆成三个步骤：

1. 创建草稿
2. 确认正文内容已上传
3. 显式执行发布

这样拆的原因是，内容创建本身就包含两类完全不同的数据：

- 结构化元数据：标题、描述、标签、可见性、作者
- 大文本正文：Markdown 或图文正文

正文体积大、更新方式特殊，而且适合走对象存储，因此系统没有把正文直接塞进事务表，而是先创建一个内容实体，再通过 OSS 上传正文，最后只把 `content_object_key`、`etag`、`sha256`、`size` 这些元信息写回主表。

这一点可以从 [createdraftlogic.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/rpc/internal/logic/knowpost/createdraftlogic.go) 和 [confirmcontentlogic.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/rpc/internal/logic/knowpost/confirmcontentlogic.go) 看出来。

### 3.1.2 为什么发布和 outbox 必须同事务

发布不是一个普通更新，而是内容生命周期里最关键的一次状态跃迁。

系统在发布时至少要保证两件事同时成立：

- `know_posts.status` 从 `draft` 变成 `published`
- 系统产生一条下游可以消费的领域事件

这里项目采用的是典型的 outbox 模式：在同一个本地事务里，既更新 `know_posts`，又插入 `outbox`。代码见 [publishlogic.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/rpc/internal/logic/knowpost/publishlogic.go)。

这样设计是为了避免最危险的一种中间状态：

- 数据库里已经是已发布
- 但搜索、索引、其他消费者永远收不到事件

如果系统改成“先提交业务表，再异步 RPC 调搜索服务”，那一旦进程在中间挂掉，就会出现不可恢复的链路断裂。Outbox 的价值，就是把“主业务提交”和“对异步世界发出可靠信号”绑定在一起。

### 3.1.3 为什么作者发帖数不放进同事务

当前发布逻辑里，作者 `posts +1` 是事务外调用的，如果失败只记日志，不回滚发布主事务。

这背后的设计判断是：

- “内容是否已发布”是主事实，必须强一致。
- “作者主页显示的发帖数”是派生统计，允许短时间最终一致。

如果把这些派生统计也一起塞进主事务，发布路径会被不必要地拉长，而且会把更多下游依赖耦合进来。当前方案是把主交易路径收短，把主事实优先保住，再接受统计视图短时延迟。

### 3.1.4 发布时序图

```text
User
  |
  | publish
  v
gateway
  |
  v
knowpost-rpc
  |
  | Tx begin
  |  1. update know_posts.status=published
  |  2. insert outbox(KnowPostPublished)
  | Tx commit
  |
  +--> invalidate cache
  |
  +--> user posts +1 (best effort)
  |
  v
Canal / Kafka
  |
  v
search-indexer
  |
  | fetch detail + fetch body
  v
Elasticsearch
```

这个时序图想强调的是：发布事务只负责“业务真相 + 可靠事件源”，而不是负责把所有读模型都同步更新完。

### 3.2 搜索索引链路

### 3.2.1 为什么搜索索引不走同步写

搜索不属于发布主交易链路的一部分。

如果发布动作同步等待 Elasticsearch 写入完成，会带来三个问题：

- 发布延迟被搜索服务拖长
- 搜索服务故障会直接影响发帖成功率
- 内容主服务和搜索服务耦合过紧

因此项目里选择的是：

- 发布时只负责写主表和 outbox
- 下游 `search-indexer` 消费事件，独立构建 ES 读模型

相关逻辑在 [processor.go](/F:/zhiguang_be/zhiguang-go/services/search/indexer/internal/processor/processor.go)。

### 3.2.2 为什么 ES 只能是读模型

这个链路里，ES 从来不是事实库。

事实永远在 `know_posts` 主表，ES 只是为了支持下面这些访问形态：

- 关键词匹配
- 检索排序
- suggest / 搜索推荐

也正因为 ES 只是读模型，indexer 收到事件后并不是盲写，而是会回拉内容详情，再根据当前真实状态决定：

- 如果是 `published + public`，则 upsert 到索引
- 如果已经撤稿或改成私有，则做 soft delete

这样做的好处，是搜索索引最终一定以主表状态为准，而不会把旧状态当成真相。

### 3.2.3 为什么只有公开已发布内容进入搜索

项目当前把“能不能被搜索到”明确绑定到了内容可见性和内容状态上：

- `status=published`
- `visible=public`

这符合一期“公共知识广场”的定位。

搜索系统本质上是公共内容发现能力，而不是私有草稿检索系统。因此草稿、不公开内容都不应该进入 ES。

### 3.3 公共 Feed 链路

### 3.3.1 为什么一期只做全局公共流

当前项目的公共 feed 不是 personalized timeline，而是全局公共流，底层查询逻辑也很直接：读取 `published + public` 内容，按 `publish_time desc` 排序。可以在 [knowpostsmodel.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/shared/model/knowpostsmodel.go) 看到这点。

这背后的判断是：

- 一期是公共内容广场，不是强关系社交产品。
- 与其过早引入推拉模型、扇出、回填、收件箱设计，不如先把公共内容流稳定跑通。

这属于一个很典型的业务边界收敛：先做用户都能看到的公共知识流，而不是一开始就承诺复杂的个性化分发。

### 3.3.2 为什么公共 feed 要做多级缓存

公共流最先遇到的瓶颈一般不是写，而是读。

因为首页流量会不断重复读取相近的分页数据，所以项目围绕公共 feed 做了分层缓存：

- L1 本地整页缓存
- Redis 整页缓存
- Redis ids 列表缓存
- Redis 单条 item 缓存
- singleflight 防止并发 miss 一起回源

相关逻辑在 [getpublicfeedlogic.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/rpc/internal/logic/knowpost/getpublicfeedlogic.go)。

这套设计的核心不是“多加几层缓存”，而是对读放大问题做了分解：

- 整页缓存解决首页热门页的高频读取
- item 缓存解决跨页复用
- ids 列表解决页重建
- singleflight 防止缓存击穿时所有请求一起打 DB

### 3.3.3 为什么要维护反向索引失效

缓存一旦做细，失效就会变复杂。

项目这里没有选择“更新一条内容就把所有 feed 缓存全删掉”，而是维护了 `feed:public:index:{postId}:{hourSlot}` 这样的反向索引，用来记录某条内容出现过哪些页面。代码在 [keys.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/rpc/internal/cache/keys.go) 和 [cache_invalidation_helper.go](/F:/zhiguang_be/zhiguang-go/services/knowpost/rpc/internal/logic/knowpost/cache_invalidation_helper.go)。

这样做的好处是：

- 失效更精确，不会一改一条内容就把整片缓存雪崩掉
- 可以针对受影响页面做定向清理

代价也很明确：

- 写路径需要维护更多缓存关系
- 失效逻辑更复杂，排查成本更高

这就是一个非常典型的 trade-off：为了更高的读性能和更低的缓存误伤，接受失效逻辑的复杂性上升。

### 3.4 点赞收藏回流链路

### 3.4.1 为什么先存“用户动作事实”，再存“总数展示”

点赞收藏这类场景，最根本的问题不是“总数是多少”，而是：

> 某个用户是否已经对某个实体执行过这个动作？

这决定了它首先是一个集合成员问题，而不是一个普通计数器问题。

因此项目把它拆成两层：

- 事实层：用户是否点过赞/收藏
- 展示层：总点赞数/总收藏数

事实层使用 Bitmap 表达，展示层使用聚合后的 SDS 快照表达。这样做是因为两者的访问形态完全不同：

- 事实层要求幂等、去重、状态切换简单
- 展示层要求高频读取、低延迟返回

### 3.4.2 为什么不用单 Redis 计数器或 MySQL 聚合

如果只用单 Redis String 自增，会遇到两个问题：

- 很难表达“某用户是否已经点过”
- 幂等切换逻辑容易和总数耦合，错一次就很难修

如果每次都落 MySQL 再聚合，又会让高频互动写入和高频计数读取都变得很重。

当前项目的做法是：

- 先把行为真相写入 Bitmap
- 真正发生状态变化时，才发 Kafka 事件
- `aggregator` 把变更聚合进 `agg:*` Hash 桶
- `flusher` 再把聚合值折算进 `cnt:*` SDS 快照

对应代码：

- [togglelogic.go](/F:/zhiguang_be/zhiguang-go/services/counter/rpc/internal/logic/counter/togglelogic.go)
- [flusher.go](/F:/zhiguang_be/zhiguang-go/services/counter/aggregator/internal/flusher/flusher.go)
- [schema.go](/F:/zhiguang_be/zhiguang-go/services/counter/shared/schema/schema.go)
- [keys.go](/F:/zhiguang_be/zhiguang-go/services/counter/shared/schema/keys.go)

### 3.4.3 为什么这套设计可以接受最终一致

这套方案的关键前提是：

- Bitmap 才是事实层
- Kafka 聚合流和 SDS 快照只是投影层

所以即使出现“位图写成功，但事件发送失败”的情况，系统也不是永久错账。

项目里已经设计了两层恢复机制：

1. 读时自愈
   - 当 `GetCounts` 发现 SDS 缺失时，会扫描 Bitmap 全量 `BITCOUNT` 重建快照。
2. 后台对账
   - `reconciler` 会定期比对 SDS 和 Bitmap 的差异，超阈值就回写修正。

相关逻辑在 [getcountslogic.go](/F:/zhiguang_be/zhiguang-go/services/counter/rpc/internal/logic/counter/getcountslogic.go) 和 [worker.go](/F:/zhiguang_be/zhiguang-go/services/counter/reconciler/internal/worker/worker.go)。

所以这套系统真正表达的不是“我完全不在乎一致性”，而是：

> 我接受展示总数短时间漂移，但我不接受永久错账。

## 4. 数据库表设计（Schema）

### 4.1 `know_posts`

`know_posts` 是内容主事实表，设计上最重要的不是字段多，而是边界清晰：

- 正文不直接存全文，而是只保留对象存储元信息
- `status`、`visible`、`publish_time` 共同描述内容生命周期
- 标签和图片等弱结构化字段采用 JSON 存储，兼顾灵活性

在索引设计上，这张表也不是泛泛建索引，而是围绕实际查询建的：

- `ix_know_posts_creator_ct`
  - 支撑作者内容管理和个人内容列表
- `ix_know_posts_status_ct`
  - 支撑按状态筛选内容
- `ix_know_posts_tag_ct`
  - 支撑内容分类扩展
- `ix_know_posts_top_ct`
  - 支撑置顶内容读取
- `ix_know_posts_creator_status_pub`
  - 支撑作者维度和发布时间维度的组合查询

这张表的本质，是内容事实源，而不是内容检索源。

### 4.2 `outbox`

`outbox` 在这个项目里不是普通日志表，而是一个非常核心的架构组件。

它承担的是“把事务世界和异步世界接起来”的责任：

- 上游事务提交时，把领域事件以 JSON payload 形式写入 outbox
- 下游通过 Canal / Kafka 订阅 outbox，再去构建搜索索引、关系镜像、其他投影

它存在的原因，是为了避免“业务提交成功，但下游扩散丢失”这种不可恢复状态。

换句话说，`outbox` 让系统用一个本地事务，换掉了原本很脆弱的跨服务同步调用。

### 4.3 `following` / `follower`

关系链路里，`following` 和 `follower` 的拆分也体现了建模上的取舍。

`following` 是主事实表：

- 表示 `from_user -> to_user` 的关注关系是否存在
- 写路径强一致维护它

`follower` 是反向镜像表：

- 主要为了按“某用户有哪些粉丝”高效查询
- 由 syncer 异步消费事件后补齐

这说明项目在关系建模上采用的是：

> 主事实同步维护，反向视图异步生成。

这样做的代价是，粉丝列表和计数可能短时间延迟；但好处是，关注主写路径更短、更稳。

### 4.4 `users` / `login_logs`

`users` 是主资料表，`login_logs` 是行为与审计日志表。

这个拆分的价值在于：

- 用户资料查询不会被行为日志污染
- 登录轨迹、渠道、IP、状态等信息可以独立追踪
- 主业务和审计型数据职责分离

## 5. Redis 键值设计（KV Design）

### 5.1 Feed 缓存键设计

内容和 feed 相关的 Redis key 不是随意命名，而是有明显的层次：

- `knowpost:detail:{id}:v{ver}`
  - 内容详情缓存
- `feed:public:{size}:{page}:v{ver}`
  - 公共 feed 整页缓存
- `feed:public:ids:{size}:{hourSlot}:{page}`
  - 公共 feed 页内 ids 列表
- `feed:item:{id}`
  - 单条 feed item，供跨页复用
- `feed:public:index:{postId}:{hourSlot}`
  - 某个帖子出现过哪些页的反向索引

这样的设计体现出三个思路：

1. 读热点以页为单位缓存
2. 复用热点以 item 为单位缓存
3. 失效定位通过反向索引精确命中

此外，key 里带 `v{ver}` 也不是多余的，它意味着当缓存布局发生升级时，可以通过版本号统一废弃旧缓存，而不需要做脏数据兼容。

### 5.2 Counter 键设计

计数系统的 key 空间分层更明显：

- `bm:{metric}:{etype}:{eid}:{chunk}`
  - 用户行为事实位图
- `agg:v1:{etype}:{eid}`
  - 聚合桶
- `cnt:v1:{etype}:{eid}`
  - 读优化 SDS 快照

它们分别对应：

- 真相层
- 中间折算层
- 对外查询层

这种键空间设计本身就说明，这不是“拿 Redis 当缓存随便用”，而是在显式构建多层读模型。

### 5.3 Relation 键设计

关系链路里的 ZSet 缓存也有明确的职责边界：

- `uf:flws:{userId}`
  - 某用户关注列表
- `uf:fans:{userId}`
  - 某用户粉丝列表

但这里要特别强调一点：

这些 ZSet 只服务列表查询，不承担关系真相。

关系真相仍然在 `following` 主表里，因此像 `Status` 这样的查询直接查 DB，而不是查缓存。这样做是为了保证“是否已关注”这个判断尽可能准确、简单。

### 5.4 TTL 与热 Key 策略

项目里的缓存策略不是简单设置固定 TTL，而是做了几层处理：

- 基础 TTL
- TTL 抖动
- 热点命中后延长过期时间

这样做主要是为了应对两个问题：

- 大量 key 在同一时间过期，导致缓存雪崩
- 热点页或热点 item 刚过期就被高并发回源

所以 Redis 在这里并不是单纯为了“更快”，而是为了让读峰值更平滑、更可控。

## 6. 设计原因与技术选型（Why）

### 6.1 为什么正文进 OSS，不进 MySQL

对比两个方案：

- 方案 A：正文直接存 MySQL
- 方案 B：正文存 OSS，主表只存元信息

最终选 B，主要是因为：

- 正文体积大，不适合和事务型元数据长期混在一起
- 上传链路更适合对象存储直传
- 后续内容检索、内容回拉、索引构建都可以通过 `content_url/object_key` 统一处理

代价是：

- 内容访问路径变长
- 需要额外维护 OSS 元数据与内容存在性校验

### 6.2 为什么发布走 Outbox，而不是同步调用搜索服务

对比两个方案：

- 方案 A：发布后同步 RPC 调搜索服务写索引
- 方案 B：发布与 outbox 同事务提交，由下游异步构建索引

最终选 B，原因是：

- 搜索不是发布主交易的一部分
- 同步 RPC 会把下游故障放大到主交易成功率
- Outbox 可以避免“主业务成功但扩散丢失”的断裂

代价是：

- 搜索结果存在短时间最终一致
- 需要维护额外的消费与重试链路

### 6.3 为什么一期只做公共 feed，不做关注时间线

对比两个方案：

- 方案 A：一期就做完整的关注时间线系统
- 方案 B：一期只做全局公共知识广场

最终选 B，原因是：

- 业务目标是先验证内容生产和消费闭环
- 关注时间线会引入推拉模型、扇出、大 V 分发、收件箱等复杂度
- 过早优化社交分发，会让项目在 MVP 阶段承担过重架构成本

代价是：

- 分发精度不如个性化 feed
- 暂时无法体现强社交场景能力

### 6.4 为什么计数采用 Bitmap + Kafka + SDS

对比几个方案：

- 方案 A：MySQL 记录行为，每次聚合 count
- 方案 B：单 Redis 计数器同步自增
- 方案 C：Bitmap 表事实，Kafka 做变更流，SDS 做查询快照

最终选 C，原因是：

- Bitmap 天然适合表达“用户是否做过某动作”
- 只有事实层稳定，幂等和切换逻辑才简单
- 总数展示适合做异步折算，避免把高频读写硬绑在一起

代价是：

- 实现复杂度明显上升
- 需要重建和对账机制兜底

### 6.5 为什么关系链路采用主表 + 镜像表 + ZSet

对比两个方案：

- 方案 A：一张关系表扛所有读写
- 方案 B：主表维护关系真相，镜像表和 ZSet 面向读优化

最终选 B，原因是：

- 关注写入最重要的是关系事实准确落地
- 粉丝反查、分页列表、热门读取适合单独优化
- 把读优化异步化，可以保持写路径更短

代价是：

- 粉丝列表和数字可能短时间滞后
- 系统里会存在多个关系读模型

## 7. Trade-off（权衡与妥协）

> 这个项目最核心的取舍不是“要不要做高性能”，而是“什么必须强一致，什么可以最终一致”。

### 7.1 发布主链路强一致，搜索和统计最终一致

为了保证发布动作稳定，系统把“已发布”这个事实放在最优先级。

因此：

- 主表状态更新和 outbox 事件插入必须同事务
- 搜索索引刷新允许稍后到达
- 作者发帖数允许稍后对齐

这相当于用少量读延迟，换主交易路径的稳定性。

### 7.2 为了读性能，引入复杂缓存失效

公共 feed 是典型高读场景，所以项目愿意在缓存层投入更多复杂度：

- 多级缓存
- 页缓存 + item 缓存
- 反向索引失效
- 热点页 TTL 延长

好处是首页读流量更稳，坏处是失效逻辑明显更重。

### 7.3 为了高吞吐计数，接受读模型漂移

点赞收藏总数不是同步强刷，而是异步折算。

这意味着：

- 系统可能出现短时间计数延迟
- 但不会接受永久错账

因此项目额外引入了：

- 读时自愈
- 后台对账

这是一种典型的工程性妥协：不是追求瞬时完美，而是追求高吞吐下的可恢复正确性。

### 7.4 为了写路径短，把关系镜像异步化

关系链路中，关注成功最重要的是主事实入库成功。

至于：

- 粉丝列表缓存
- ZSet 最近列表
- 粉丝数/关注数

这些都被下放到异步镜像阶段。

这样做的好处是写路径稳，代价是用户刚关注后，列表和数字可能存在轻微滞后。

## 8. 风险点与面试追问准备

### 8.1 公共 feed 流量继续放大时，最先扛不住什么

如果公共流量继续放大，最先暴露风险的通常不是写入，而是：

- 缓存失效后的回源 DB 压力
- 热点内容更新导致的失效风暴

因此这套架构更像是在用多级缓存和 singleflight 尽量推迟 DB 成为瓶颈的时间点。

### 8.2 Outbox 积压会带来什么问题

如果 outbox 消费链路积压，影响最大的不是内容发布本身，而是：

- 搜索结果变旧
- RAG 索引变旧
- 各类异步投影延后

这再次说明系统把主业务提交和下游可见性做了优先级分层。

### 8.3 Bitmap 写成功但 Kafka 失败怎么办

这是计数设计最典型的追问点。

这里最关键的回答不是“我们尽量不失败”，而是：

- Bitmap 已经把用户动作事实保住了
- Kafka 失败只会影响派生总数
- SDS 可以通过 Bitmap 回扫重建
- 定时 reconciler 可以进一步修正漂移

也就是说，系统承认短时间不一致，但不承认永久错误。

### 8.4 热点内容频繁修改时怎么办

热点内容如果被频繁修改，会触发：

- 详情缓存失效
- item 缓存失效
- 公共页反向索引命中后的页缓存失效

这会导致热点内容附近页面重复回填，因此公共流的热点变更场景是一个天然要重点观察的风险区。

### 8.5 面试时最值得强调的三句话

最后如果要把整个项目压缩成最值得面试官记住的三句话，我会这么讲：

1. 一期我刻意把业务收敛成“公共知识广场”，不急着做复杂关注时间线。
2. 我把内容主表、搜索索引、缓存页、计数快照明确拆成“事实层”和“投影层”。
3. 我的重点不是让所有链路都强一致，而是识别哪些必须强一致，哪些可以最终一致但要可恢复、可对账。

## 9. 总结

这个项目真正想体现的能力，不是“我会搭很多中间件”，而是下面三件事：

- 我能先把业务边界收敛清楚，避免一开始过度设计。
- 我能把同步主链路和异步扩散链路拆开，明确哪些数据是事实、哪些数据是读模型。
- 我能在高读高并发场景下，用缓存、异步聚合和最终一致性换性能，同时又通过重建和对账把正确性兜住。

如果从面试官视角看，这类项目最有说服力的地方，不是“功能很多”，而是：

> 你不仅知道系统怎么跑，还知道它为什么要这样跑，以及它为此放弃了什么。
