# Feed 推拉混合架构全面性能与压力测试设计

日期：2026-08-14

## 1. 背景

KnowPost 已实现基于粉丝数阈值的推拉混合 Feed：普通作者发布后通过 Kafka 异步扇出到粉丝 Inbox，大 V 作者只写 Outbox，用户读取时归并 Inbox 与所关注大 V 的 Outbox。

现有压测工具具备基础 RPC 发布和读取能力，但不足以形成可信的架构对比报告：

- 当前测试数据没有真正构造粉丝数超过 1,000 的大 V，无法稳定触发拉模式。
- 独立读取工具调用的是公共 Feed，而不是个性化 `GetUserFeed`。
- 只有平均延迟，P50、P95、P99 和最大延迟缺失或使用估算值。
- 网关没有暴露个性化 Feed HTTP 接口，无法衡量 Gateway 到 RPC 的端到端开销。
- 缺少纯推、纯拉、混合三种策略在相同数据集、相同负载下的公平对照。
- 缺少 Kafka lag、Redis、MySQL 和应用容器资源指标，无法解释性能拐点的根因。

本设计建立一套可复现的测试体系，主要回答两个问题：

1. 当前单机开发环境下，Feed 写入、读取和混合负载的峰值、稳定吞吐与性能拐点在哪里。
2. 在相同数据与负载下，纯推、纯拉、推拉混合分别承担了怎样的写放大、读放大和异步积压成本。

SLA 指标只作为结果解释的参考线，不作为压测是否成功的唯一判据。

## 2. 目标与非目标

### 2.1 目标

- 使用同一份用户、关注关系和内容数据，对比 `push`、`pull`、`hybrid` 三种策略。
- 分别测量直连 KnowPost RPC 和 Gateway HTTP 两条入口。
- 覆盖写、读、混合、热点、分散、深分页、突发和阶梯加压场景。
- 记录客户端延迟分位数、吞吐、错误率和正确性指标。
- 记录 Kafka lag 与清空时间、Redis/MySQL 指标以及核心容器 CPU/内存。
- 自动生成 JSON、CSV 和 Markdown 报告，报告包含环境、参数、结果和局限性。
- 所有测试数据带唯一 `run_id`，允许重复运行并支持定向清理。

### 2.2 非目标

- 不将本地单机数据外推为生产集群容量。
- 不在本轮引入推荐排序、内容质量打分或 Feed 排名算法。
- 不把推拉阈值改造成线上自动调参系统。
- 不为了压测重构无关服务或更换 Redis、Kafka、MySQL 实现。
- 不承诺 Exactly-Once；现有语义仍为 At-Least-Once 加业务幂等收敛。

## 3. 方案选择

### 3.1 主方案：相同数据集强制切换策略

新增 Feed 策略配置：

```yaml
Feed:
  Strategy: hybrid
```

支持值：

- `push`：所有作者都发送 Kafka fanout 事件。
- `pull`：所有作者都只写作者 Outbox。
- `hybrid`：粉丝数不超过 1,000 走推，超过 1,000 走拉。

默认值始终为 `hybrid`。非法值导致服务启动失败，避免误用时静默降级到错误策略。

该方案保证三轮测试复用相同作者、粉丝关系、帖子数量、并发和请求顺序，策略是唯一主要变量。

### 3.2 补充方案：自然阈值验证

在 `hybrid` 模式下同时创建普通作者和真实大 V，通过 Counter 快照确认两类作者分别落在阈值两侧，验证配置对照结果没有偏离实际分流逻辑。

### 3.3 组件级诊断

保留和扩展现有 Feed 单元测试与 Benchmark，用于解释 Redis Pipeline、Top-N 堆、候选回填和批量详情加载的局部成本。组件 Benchmark 不作为端到端容量结论。

## 4. 代码与组件设计

### 4.1 Feed 策略配置

在 KnowPost RPC 配置中增加 Feed 策略，并通过 ServiceContext 注入 FeedWriter。策略判断集中在 Feed 包中，发布 Logic 不直接包含压测分支。

生产和普通开发配置使用 `hybrid`。压测 Compose override 为三种模式提供独立配置，切换模式时只重启 KnowPost 容器，不重建依赖组件。

### 4.2 Gateway 个性化 Feed 接口

新增鉴权接口：

```text
GET /api/v1/knowposts/following-feed?page=1&size=20
```

Gateway 从已验证 Token 的上下文获取用户 ID，调用 KnowPost RPC `GetUserFeed`，并返回与现有 Feed HTTP 响应一致的 JSON 结构。客户端不能通过查询参数伪造其他用户 ID。

网关当前没有 Feed 限流中间件；压测工具直接请求 Gateway 即绕过前端限流，不删除后端安全或恢复中间件。

### 4.3 压测工具

重构 `cmd/loadtest` 为一个可测试的命令行工具，提供以下阶段：

- `setup`：创建测试用户、作者、阅读者、关注关系和预热内容。
- `smoke`：验证三种分流结果、Inbox/Outbox 和 Feed 可见性。
- `run`：执行指定入口、策略和负载场景。
- `compare`：汇总相同 `run_id` 下的三种策略结果。
- `cleanup`：删除该 `run_id` 关联的 MySQL、Redis 测试数据。

入口模式：

- `rpc`：通过 etcd 发现直连 KnowPost、Relation、Counter、User RPC。
- `gateway`：通过 HTTP 和真实访问令牌调用 Gateway。

工具应支持按固定请求数和固定时长运行，并使用固定随机种子实现请求序列复现。

### 4.4 延迟与结果记录

每个测试阶段独立记录成功请求延迟，生成：

- Min、Mean、P50、P90、P95、P99、Max。
- 总请求数、成功数、失败数、超时数和成功 QPS。
- 发布流程 Draft、Metadata、Confirm、Publish 各阶段延迟。

单阶段完成后再排序计算分位数；每个阶段释放样本，避免跨场景累积内存。报告不得使用估算延迟。

### 4.5 监控采集

测试编排脚本按固定周期采集：

- Docker：Gateway、KnowPost、Relation、Counter 的 CPU 与内存。
- Kafka：`feed-fanout-group` 当前 lag、峰值 lag、施压结束后的清空时间。
- Redis：内存、命令数、网络输入输出、key 数和命中率。
- MySQL：Questions、Threads_connected、Threads_running 和慢查询计数。
- 应用：服务 Prometheus 指标及日志中的 timeout、panic、重试和容器重启。

采集失败会记录为报告缺失项，但不会伪造数值；核心请求结果和 Kafka lag 采集失败则使该轮报告标记为不完整。

## 5. 测试数据设计

### 5.1 正式默认数据集

- 粉丝用户：1,200 至 1,500。
- 普通作者：20，每人约 100 个粉丝。
- 大 V 作者：5，每人至少 1,100 个粉丝。
- Feed 阅读用户：20 至 50，同时关注普通作者和大 V。
- 每类作者预热若干帖子，保证首页、热点和深分页均有候选数据。

具体规模保留为配置项。正式运行前先用小数据冒烟，再创建完整数据集。

### 5.2 数据隔离

- 每次运行生成唯一 `run_id`。
- 用户标识、昵称、帖子标题和内容对象键包含 `run_id`。
- 工具保存创建的用户 ID、帖子 ID 和 Redis key 清单。
- 清理只删除该 `run_id` 对应的数据，不扫描或删除无法归属的业务数据。
- 无论成功或失败，测试结束时都把 KnowPost 策略恢复为 `hybrid`。

## 6. 测试矩阵

### 6.1 功能冒烟

每种策略至少验证：

- 作者本人能看到刚发布内容。
- `push` 模式产生 Kafka 扇出并写入粉丝 Inbox。
- `pull` 模式写作者 Outbox，不执行粉丝扇出。
- `hybrid` 中普通作者走推、大 V 走拉。
- Feed 返回同时包含普通作者和大 V 内容，无重复项。
- Kafka lag 最终清零。

冒烟失败时停止正式压测并进入根因诊断。

### 6.2 负载场景

| 场景 | 说明 | 主要结论 |
|---|---|---|
| 写入基线 | 低并发完整发布链路 | 单请求基础成本 |
| 纯发布阶梯 | 逐级增加发布并发 | 发布能力、扇出能力和积压拐点 |
| 冷读取 | 清理 Feed 缓存后读取 | DB/RPC 回源成本 |
| 热读取 | 缓存预热后持续读取首页 | 稳态最大读吞吐 |
| 热点读取 | 流量集中到少量用户 | 热 key 与单用户 Inbox 成本 |
| 分散读取 | 多用户随机读取 | Relation/Counter 和 Redis 并发能力 |
| 深分页 | 随机读取后续页面 | 候选倍增、批查和 Top-N 成本 |
| 混合 90/10 | 90% 读、10% 发布 | 典型读多写少负载 |
| 混合 80/20 | 80% 读、20% 发布 | 写入增强后的资源竞争 |
| 突发并发 | 从空闲瞬间升到目标并发 | 冷启动失败与恢复能力 |
| 停止施压 | 停止请求后继续观察 | Kafka lag 清空和延迟恢复 |

### 6.3 入口覆盖

- 三种策略首先在 RPC 入口完成全部核心对照，隔离 Feed 服务能力。
- Gateway 至少覆盖热读取、分散读取、完整发布和 90/10 混合场景。
- Gateway 与 RPC 使用同一数据集和负载参数，报告给出 Gateway 附加延迟和吞吐损耗。

## 7. 阶梯加压与容量定义

### 7.1 阶梯加压

默认并发阶梯为：

```text
1, 2, 4, 8, 16, 32, 64, 128, 256
```

每阶包含短预热和稳定采样窗口。若 256 并发尚未出现吞吐拐点，可继续倍增；若出现持续高错误率、容器重启或数据库不可用，则停止继续加压并进入恢复观察。

### 7.2 容量口径

报告同时给出：

- 峰值吞吐：任一稳定采样窗口观察到的最高成功 QPS。
- 稳定吞吐：在错误和积压不持续扩大的情况下可维持的吞吐。
- 性能拐点：增加并发后吞吐提升不足 10%，同时延迟、错误或积压明显增长的首个阶段。
- 异步容量：Kafka fanout 的峰值输入速度、稳定消费速度、峰值 lag 和清空时间。
- 恢复时间：停止施压后 Kafka lag、错误率和延迟恢复稳定所需时间。

参考 SLA 仅用于辅助阅读，例如 P95、P99 和错误率，不覆盖上述容量口径。

## 8. 推、拉、混合的预期取舍

报告不预设胜负，但应验证以下假设：

- 纯推：Feed 读取最轻；发布成本随粉丝数增长，Kafka 和 Redis 写入成为主要瓶颈。
- 纯拉：发布成本稳定；读取成本随关注作者数和 Outbox 数增长，Relation、Counter 与 Redis 读取成为主要瓶颈。
- 混合：普通作者承担可控写扩散，大 V 转移到读时归并；峰值通常不等于两者最佳值，但读写尾延迟和资源风险应更均衡。

若实测不符合假设，以指标、日志和资源数据为准，不修改报告结论来迎合设计预期。

## 9. 错误处理和测试完整性

- 数据准备的任何用户、关系或内容创建失败都立即终止该轮。
- 每个请求设置超时并区分业务错误、RPC/HTTP 错误和客户端超时。
- 请求返回成功但 Feed 内容不符合预期时计为正确性失败。
- 正式阶段不以固定 `sleep` 代替 Counter 同步或 Kafka 完成判断，而是轮询可验证状态并设置截止时间。
- 压测过程中出现 bug 时，先添加最小回归测试，再修改生产代码。
- 报告明确列出未完成场景、缺失指标、环境噪声和本地单机局限性。

## 10. 容器加载与执行

- 继续使用 `deploy/compose/docker-compose.dev.yml` 的现有依赖和数据卷。
- 使用 Docker BuildKit 缓存重建应用镜像；`go mod download` 和 Go build cache 在依赖未变化时复用。
- 不重建或清空 MySQL、Redis、Kafka、etcd、Elasticsearch 数据卷。
- 代码变更后只重新创建受影响的 Gateway、KnowPost 等应用容器。
- 策略切换通过压测配置或 Compose override 完成，避免每轮重新构建镜像。

## 11. 验证与交付

### 11.1 自动化验证

- Feed 策略配置和非法值测试。
- 三种策略路由测试。
- Gateway 个性化 Feed 鉴权与参数测试。
- 压测数据拓扑测试，确保大 V 粉丝数确实超过阈值。
- 延迟分位数、结果校验和不完整报告测试。
- 现有 Feed、KnowPost、Relation、Gateway 回归测试。

### 11.2 最终交付

- 可重复运行的 RPC/Gateway Feed 压测工具。
- 三种策略的配置与 Compose 执行方式。
- 原始 JSON/CSV 结果。
- Markdown 综合报告，包含单机容量、性能拐点、推拉取舍和局限性。
- 发现并修复的问题及对应回归测试。

## 12. 实施顺序

1. 运行现有单元测试并记录基线。
2. 使用当前混合模式构建应用镜像并完成小流量冒烟。
3. 以测试先行方式加入策略配置与 Gateway 接口。
4. 重构压测数据准备、统计和双入口执行能力。
5. 加入监控采集和结构化报告。
6. 依次运行纯推、纯拉、混合的 RPC 测试。
7. 运行 Gateway 对照测试。
8. 对失败与性能异常做根因分析和回归修复。
9. 汇总最终报告并将服务恢复到 `hybrid`。
