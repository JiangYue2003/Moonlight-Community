# Feed WP11 写入/混合负载 Control 阶段报告

日期：2026-08-19  
状态：历史阶段报告；已被 [2026-08-27 RPC 正式 A/B 报告](2026-08-27-feed-wp11-mutation-rpc-ab.md) 取代

> 本文使用 2026-08-19 的旧 checkpoint 和 RPC/Gateway 折中矩阵，只用于保留 Control 阶段历史。2026-08-27 已在新鲜严格基线上完成 RPC-only Control/Treatment；后续 Gateway 性能测试按用户决策取消。

## 1. 结论摘要

本阶段已经得到一份可复核的写入/混合负载基线，但还不能计算优化前后的提升百分比：

- Control 正式报告共 36 轮，36/36 为 `complete=true`。
- 累计完成 10,253 个完整发布流程和 44,114 次个性化 Feed 读取，失败数和超时数均为 0。
- 36/36 次测量后数据恢复成功；最终独立 checkpoint 校验为 `complete=true`。
- 单纯发布的稳定并发是 c2，c4 已接近延迟拐点。
- 90/10、80/20 混合负载的稳定并发是 c4；c8 基本不能提高总吞吐，却让发布 P95 接近翻倍。
- 当前完整发布流程的吞吐平台约为 4.4–5.4 次/秒。这里的一次“发布”不是一次 RPC，而是依次完成创建草稿、修改元数据、确认内容、正式发布四个 RPC。
- 混合压力下 Feed 读路径仍然稳定：c4 的 RPC 读取 P95 约 3.2ms，Gateway 读取 P95 约 3.9–4.0ms；c8 时 P95 上升到约 5.3–6.5ms，但没有失败。
- Treatment 尚未执行，因此当前数字只回答“旧路径在真实写入和读写竞争下能承载多少”，不能回答“优化提升了多少”。

## 2. 为什么这组测试耗时且复杂

写入压测与纯读压测不同。一次发布会同时改变 MySQL 帖子、Outbox、Redis Inbox/BigV ZSET、缓存安全版本，并通过 Kafka 异步触发 Feed 扇出。如果连续运行而不恢复，后面的轮次面对的是越来越大的数据集，三轮结果不能比较，Control/Treatment 也不再是严格 A/B。

因此每个正式 trial 都固定执行：

1. 校验 Kafka 已稳定排空、checkpoint、代码和进程身份一致。
2. 从相同 checkpoint 恢复基线数据并递增安全版本。
3. 预热 10 秒。
4. 再次恢复，清除预热产生的帖子和缓存影响。
5. 正式采样 60 秒。
6. 等待 Kafka 恢复至 lag=0。
7. 删除本轮生成的精确帖子和 Outbox，恢复 Redis Feed 数据并校验指纹。

一次 60 秒测量实际需要约 90–100 秒。原始全矩阵为 3 个场景 × 2 个入口 × 4 个并发 × 3 轮 × 2 个预设，共 144 个正式 trial，预计需要 4–6 小时。经批准后采用折中矩阵，缩减为每个预设 36 个 trial、Control/Treatment 合计 72 个 trial；本次已经完成前 36 个 Control trial。此前为了寻找并发拐点还运行过短时 scout，这也是总耗时明显超过 60 分钟的原因之一。

## 4. 正式结果

以下均为三轮中位数。混合场景的总成功吞吐等于读 QPS 与完整发布流程 QPS 之和。

### 4.1 单纯发布

| 入口 | 并发 | 完整发布 QPS | 发布 P95 | 判断 |
|---|---:|---:|---:|---|
| RPC | 2 | 4.39 | 606.51ms | 稳定档 |
| RPC | 4 | 4.68 | 1041.13ms | 吞吐仅增加 6.6%，P95 增加 71.7% |
| Gateway | 2 | 4.68 | 525.87ms | 稳定档 |
| Gateway | 4 | 4.98 | 980.21ms | 吞吐仅增加 6.4%，P95 增加 86.4% |

结论：发布吞吐在约 5 个完整流程/秒附近进入平台期。c4 不能带来与并发增长相匹配的吞吐，只会增加排队时间，因此 c2 是更合理的稳定工作点，c4 是相邻拐点。

### 4.2 90% 读、10% 写

| 入口 | 并发 | 读 QPS / P95 | 发布 QPS / P95 | 总 QPS |
|---|---:|---:|---:|---:|
| RPC | 4 | 41.25 / 3.16ms | 4.58 / 1009.85ms | 45.83 |
| RPC | 8 | 43.28 / 5.28ms | 4.81 / 1845.81ms | 48.09 |
| Gateway | 4 | 41.08 / 3.99ms | 4.56 / 1019.50ms | 45.64 |
| Gateway | 8 | 39.41 / 6.47ms | 4.38 / 2237.82ms | 43.79 |

结论：RPC 从 c4 增到 c8 时总吞吐只增加约 4.9%，发布 P95 增加约 82.8%；Gateway 总吞吐反而下降约 4.1%，发布 P95 增加约 119.5%。c4 是明显更好的稳定点。

### 4.3 80% 读、20% 写

| 入口 | 并发 | 读 QPS / P95 | 发布 QPS / P95 | 总 QPS |
|---|---:|---:|---:|---:|
| RPC | 4 | 20.08 / 3.17ms | 5.02 / 931.31ms | 25.10 |
| RPC | 8 | 19.67 / 5.41ms | 4.92 / 1774.20ms | 24.59 |
| Gateway | 4 | 19.87 / 3.92ms | 4.97 / 922.04ms | 24.84 |
| Gateway | 8 | 21.40 / 6.03ms | 5.35 / 1642.85ms | 26.75 |

结论：RPC c8 的吞吐已经下降；Gateway c8 虽提高约 7.7% 总吞吐，但发布 P95 增加约 78.2%。综合吞吐、延迟和资源余量，c4 仍是稳定工作点，c8 是过载边界探针而不是推荐档。

## 5. 数据正确性与隔离证据

- 36 份正式报告全部完整，所有业务阶段失败数和超时数均为 0。
- 正式采样共生成 10,253 个帖子 ID；每一轮报告都证明本轮 ID 被纳入精确删除集合。
- 预热阶段额外生成并清理 1,955 个帖子，未进入正式测量初态。
- 36/36 次 after-trial restore 成功，恢复耗时中位数 4.961 秒，范围 4.895–5.128 秒。
- Kafka 恢复耗时中位数 5.54 秒，范围 5.26–7.30 秒；采样中出现的短时 lag 最终都回到 0。
- Redis eviction 和 rejected connection 均为 0；最终独立 checkpoint 校验通过。
- 负载客户端归一化 CPU 峰值仅约 0.27%，不是本轮吞吐上限来源。

## 6. 当前暴露出的主要性能问题

### 6.1 首要瓶颈是完整写流程，不是 Feed 读取

在稳定的混合 c4 下，创建草稿 P95 约 5–13ms；元数据、内容确认、正式发布三个步骤各自 P95 大约 338–398ms，并且客户端必须串行完成。它们共同把完整流程 P95 推高到约 0.92–1.02 秒。

这意味着当前约 5 QPS 是“四阶段完整发布流程 QPS”，不能与单次 Feed 读取 QPS或此前热点读缓存的万级 QPS直接比较。后续若要提升写吞吐，应分别分析三个慢阶段的数据库事务、Outbox 写入、同步依赖和连接池等待，而不是继续提高压测并发。

### 6.2 c8 已主要增加排队，不再增加有效吞吐

混合 c8 下 KnowPost 采样 CPU 峰值约 93.75%，Redis 瞬时 ops/s 最高约 18,979；大多数场景的总吞吐只变化 -4% 到 +8%，发布 P95 却增加约 78%–120%。这符合服务进入非线性排队区的表现。

### 6.3 Gateway 不是本轮的主导瓶颈

RPC 与 Gateway 的发布吞吐都稳定在约 4.4–5.4 个完整流程/秒；稳定 c4 下混合读取差距也很小。当前后端写流程的秒级耗时远大于 Gateway 的鉴权和转发成本，因此不能把发布瓶颈归因于网关。

### 6.4 写入竞争没有击穿读取路径

即使 20% 请求执行完整发布流程，稳定 c4 的 Feed 读取 P95 仍约为 RPC 3.17ms、Gateway 3.92ms，且没有错误。这说明当前 Hybrid 读路径在本组热点数据和写入强度下具有较好的隔离性；需要优化的是写入尾延迟和容量，而不是为了这组结果改动读路径。

## 7. 当前可以与不可以下的结论

可以确认：

- Control 的稳定工作点和过载边界已经找到。
- trial 级 checkpoint/restore、Kafka 稳定排空和中断后续跑机制可以生成可比较结果。
- 当前完整写流程的平台约为 5 次/秒，c8 主要增加排队。
- 在所测热点卡上，混合写入没有显著破坏 Feed 读取正确性和毫秒级延迟。

暂时不能确认：

- Page Cache、Route Snapshot、Combined Pipeline 等 Treatment 对混合负载究竟提升还是回退多少。
- 优化是否降低 KnowPost/Relation/Redis 的单位请求成本。
- 这组结果能否外推到 1,200 或 20,000 读者的写入分布。

缺少的唯一正式对照是：使用相同 manifest、checkpoint、入口、场景、并发、时长和三轮口径，运行 36 个 Treatment trial。恢复工作时无需重跑本次 36 个 Control trial。
