# 项目结构纲领

本文规范 `zhiguang-go` 后续开发、代码生成和目录迁移的文件落点。详细契约见 `.trellis/spec/backend/directory-structure.md`。

## 1. 核心原则

- 公共业务 HTTP 只进入 `services/gateway`；Agent 是明确保留的独立入口。
- 运行代码属于 `services/<context>/internal/`；公共生成契约属于 `services/<context>/rpc/`。
- 跨 context 使用 `rpc/client/**`，禁止导入兄弟 context 的 `internal`。
- 目录迁移不得夹带 HTTP、RPC、SQL、Redis Key 或 Kafka 契约变更。
- 进程、端口或配置变化先更新 `deploy/topology/services.json`，不维护第二份服务清单。

## 2. 仓库级落点

| 目录 | 职责 |
|---|---|
| `proto/` | protobuf 源契约 |
| `services/` | bounded context、进程和内部实现 |
| `deploy/topology/` | 权威运行清单、校验器、拓扑测试 |
| `deploy/compose/` | Compose、健康检查、容器契约测试 |
| `scripts/` | 启停、迁移、代码生成脚本 |
| `docs/` | 开发者架构和运行说明 |
| `pkg/` | 与具体 context 无关的公共包 |
| `var/` | 本地二进制、缓存、日志、PID；永不提交 |

## 3. 服务内部结构

```text
services/<context>/
├── cmd/<process>/main.go      # 参数与生命周期；不放业务逻辑
├── cmd/<process>/etc/         # 进程配置
├── internal/domain/           # 确有领域不变量时才创建
├── internal/application/      # 用例、查询、编排和策略
├── internal/adapter/          # MySQL/Redis/Kafka/ES/OSS
├── internal/transport/grpc/   # RPC adapter
├── internal/transport/http/   # 仅独立 HTTP 进程
├── internal/transport/kafka/  # 消息 adapter
├── internal/bootstrap/        # 配置、组装和 Run
└── rpc/                       # 公共 protobuf/gRPC/client 生成代码
```

`application` 不依赖 `bootstrap`；`bootstrap` 负责组装；`transport` 只做协议转换和错误映射。

## 4. Gateway

- `services/gateway/internal/handler/router.go` 是唯一公共 HTTP composition root。
- `router.go` 只配置 engine/middleware 并调用 `register<Context>Routes`。
- 路由进入 `identity.go`、`content.go`、`social.go` 等所属上下文文件。
- HTTP method/path、请求响应或鉴权变化必须更新 route/auth parity 测试。
- 禁止重新创建普通业务的 `services/<context>/api`。

## 5. 代码生成

### protobuf / RPC

源文件为 `proto/<contract>/<contract>.proto`，目标为对应 context 的 `rpc/`：

```powershell
goctl rpc protoc proto/<contract>/<contract>.proto `
  --go_out=services/<context>/rpc `
  --go-grpc_out=services/<context>/rpc `
  --zrpc_out=services/<context>/rpc -m
```

- message、gRPC stub、client 保留在 `rpc/` 和 `rpc/client/**`。
- 运行实现放入 `internal/bootstrap`、`internal/application`、`internal/transport/grpc`。
- 清理由 goctl 附带生成但本项目不用的 `rpc/internal`、`rpc/etc` 和 RPC main。
- `// Code generated by goctl. DO NOT EDIT.` 文件不可手改；修改 `.proto` 后重新生成。
- 认证契约已并入 `proto/user/user.proto`，稳定 client 为 `services/user/rpc/client/auth/`；历史 `proto/auth/auth.proto` 不进入批量生成。

### go-zero API

普通业务 HTTP 由 Gateway 上下文路由承载，不再为每个 context 生成 `.api` runtime。独立 HTTP 进程才可使用 `internal/transport/http/`，且必须登记拓扑和 parity 测试。

### 数据模型

```powershell
goctl model mysql ddl -src db/migrations/<migration>.sql `
  -dir services/<context>/internal/adapter/model -c
```

model 只负责持久化映射；用例和领域规则不得写入 model 包。不同职责使用明确子目录，如 `model_auth`。

## 6. 提交前检查

1. 先判断代码属于 HTTP、RPC、worker、application 还是 adapter。
2. 生成前确认源契约、目标目录和脚本，不覆盖手写层。
3. 新进程先改 `services.json`，再改脚本、Compose、配置和文档。
4. 契约变化与目录迁移分开提交。
5. 添加 parity、配置、拓扑或 focused test。
6. 至少运行 topology validator 与受影响包 test/vet/build；跨 context 再跑完整校验。

## 7. 禁止事项

- 禁止普通业务恢复 `services/<context>/api`。
- 禁止修改生成文件来修复业务问题。
- 禁止把 RPC server、配置和业务逻辑放回 `rpc/`。
- 禁止在脚本、README、Compose 中各自维护独立服务列表。
- 禁止提交临时文件、凭据和构建缓存。
