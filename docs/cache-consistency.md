# 多级缓存与 MySQL 的一致性设计

## 1. 先说结论

本项目里缓存与 MySQL 之间**没有任何强一致机制**(没有分布式事务、没有 Change Buffer 那种同步复制),整体采用的是**Cache-Aside(旁路缓存)+ 写时显式失效**模式,提供的一致性等级是**最终一致性,且允许一个有界的过期窗口(TTL)作为兜底**。换句话说:正常路径下,写操作会尽力在提交后立刻让缓存失效或刷新,让"下一次读"读到新数据,达到近似的读己之写(read-your-writes);但如果这次失效动作因为任何原因失败(Redis 抖动、进程崩溃、网络分区),系统不会重试也不会报错阻塞主流程,只是让脏缓存活到 TTL 自然过期——这是用短暂的不一致窗口换取"缓存失效不拖累业务写入的可用性和延迟"。

理解这套设计要先分清楚项目里**两条相互独立的缓存栈**,它们的一致性策略是分开设计的:

1. **go-zero 框架自带的模型级缓存**(`sqlc.CachedConn`,只在 Model 层,如 `KnowPostsModel`/`FollowingModel`),缓存的是单行数据库记录本身。
2. **应用层的三级业务缓存**(`pkg/cachex`,L1 ristretto 本地内存 + L2 Redis + L3 业务回源),缓存的是拼装好的响应结构(详情 DTO、Feed 分页结果),以及独立于 `cachex` 之外、logic 层直接操作的 Feed 相关 Redis 结构(整页物化缓存、反向索引、ZSet 关注列表)。

## 2. 第一层:go-zero 模型级缓存(CachedConn)

`KnowPostsModel`/`FollowingModel` 等是 goctl 生成代码套 `sqlc.CachedConn`,标准行为是:`FindOne` 先查 `cache:{table}:id:{id}`(Redis),未命中才查 MySQL 并回填;`Update`/`Delete` 走框架生成的方法时,框架会**自动删除**对应的缓存 key(delete-on-write,不是 write-through 更新缓存内容,而是删除让下次读重新回源)。

但本项目里知文和关注关系的大部分写路径**没有走框架自动管理的 `Update`**,而是走自定义的 `UpdateInTx`(在外部事务里跑原生 SQL,绕开 `CachedConn`)——这是因为发布/更新知文这类操作需要和 `outbox` 表在同一个事务里提交,而 go-zero 的自动缓存删除逻辑是绑定在它自己的 `Update` 方法调用时机上的,不知道外部事务是否最终会 commit 还是 rollback,如果在事务执行中就删缓存,一旦事务后续回滚,缓存已经被删了但数据库其实没变,这本身不是错误(顶多下次多一次回源),但也不是我们想要的时机。所以项目选择手动控制:`UpdateInTx` 只管更新数据,完全不碰缓存,由调用方在**事务提交成功之后**显式调用 `InvalidateCache`(即 `sc.KnowPostsModel.InvalidateCache(ctx, id)`,内部就是 `CachedConn.DelCacheCtx`)去删这个模型缓存key。

这一层的一致性保证是:**只要"事务提交成功"和"调用 InvalidateCache"这两步都执行到,下一次 `FindOne` 就能读到新数据**;如果进程在这两步之间崩溃(事务已提交但 InvalidateCache 没来得及跑),模型缓存会残留旧值,直到 TTL 到期(go-zero `CacheConf` 里配置的过期时间)才会自然修复。这是一个已知且被接受的窗口,CLAUDE.md 里记录的历史 bug 正是这一层没做好导致的(当时是漏了 InvalidateCache 这一步,不是时序窗口问题,已经修复)。

## 3. 第二层:应用层三级缓存(`pkg/cachex`)

### 3.1 结构与读路径

`pkg/cachex.Cache[V]` 是一个通用的三级缓存抽象,`GetOrLoad` 严格按 **L1(ristretto 本地内存)→ L2(Redis)→ L3(业务提供的 loader,一般是查 MySQL)** 的顺序查找,命中哪一级就从那一级开始往回填充上层缓存(L2 命中会回填 L1;L3 回源成功会同时写 L2 和 L1)。`DetailCache`(知文详情)、`FeedMineCache`(我的Feed分页)就是用这套通用抽象实例化的。

为了不引入本文回答范围之外的复杂度,这里只强调三个跟"一致性"直接相关的机制:

- **空值哨兵(Null Sentinel)**:L3 回源查不到数据时(`ErrNotFound`),不是什么都不缓存,而是主动写一个哨兵值到 L1+L2,TTL 比正常值短(`NullTTL`)。这是防缓存穿透的标准手段,顺带产生一个一致性细节:如果一篇知文刚被创建、还没来得及被这次请求看到,前一次查询已经缓存了"不存在"的哨兵,那么在 `NullTTL` 这个窗口内,即使数据已经插入 MySQL,读缓存仍然会返回"不存在"——这是一个只影响新建数据、影响窗口等于 `NullTTL`(通常配得比正常 TTL 短,以缩小这个副作用)的已知代价。
- **单飞(SingleFlight)**:多个并发请求对同一个 key 触发 L3 回源时,只有一个真正执行 loader,其它请求等待共享结果。这解决的是"缓存击穿"(高并发对同一失效 key 的冲击),不影响一致性语义,但要注意:等待者拿到锁后会"双检"一次 L1/L2(`GetOrLoad` 内部的 double-check),这保证了单飞窗口内如果有另一个写请求恰好让缓存失效了,后续等待者不会拿到过期的回源前状态。
- **TTL 抖动(Jitter)**:每个 key 的实际 TTL 在 `BaseTTL` 基础上加一个随机抖动,防止大量 key 同一时刻集体过期造成雪崩式回源。这是可用性优化,跟一致性无关,但说明了这套缓存本身就是设计给"允许有一定过期窗口的最终一致数据"用的,不是为强一致场景设计的。

### 3.2 写路径:失效而非更新

`Cache.Invalidate` 的实现是"先删 L2、再删 L1"两步顺序删除:

```go
func (c *cache[V]) Invalidate(ctx context.Context, keys ...string) error {
    if err := c.opts.L2.Del(ctx, keys...); err != nil {
        return err
    }
    for _, k := range keys {
        c.opts.L1.Del(k)
    }
    return nil
}
```

选择"删"而不是"改"(write-through 更新缓存内容)是核心设计取舍:更新缓存内容需要在写路径上重新构造完整的缓存值(往往涉及跨表拼装,比如详情要拼计数、拼作者信息),复杂且容易出现"更新缓存的字段"与"实际写入数据库的字段"不同步的 bug;而删除后交给下一次读请求自然回源,永远读到的是数据库当下的真实状态,逻辑更简单、更不容易出错,代价是被删除的缓存到下次读之前的这段时间要多打一次数据库。项目里几乎所有写路径(`PatchMetadata`/`Publish`/`Delete`/关注取关)都遵循这个模式。

### 3.3 写前删 + 写后删(双删)

以知文写路径为例(`invalidateKnowPostCaches`,在 `PatchMetadata`/`ConfirmContent`/`Publish`/`Delete` 等每个写方法的**开头和结尾各调用一次**):

- **写前删**是为了让写方法内部的"读旧行→改字段→整行写回"（`findOwnedRow` 走 `KnowPostsModel.FindOne`,这条路径是有缓存的)读到的是新鲜数据,不会在一份过期的行上做增量修改再整行覆盖,冲掉别的并发写入——这正是 CLAUDE.md 记录的历史 bug 的根因,双删策略里的"写前删"就是专门堵这个口子的。
- **写后删**是为了清掉写操作执行期间可能被并发读请求重新写入的缓存(经典的"延迟双删"要解决的竟态:线程A删缓存→读DB→线程B写DB→线程B删缓存(此时A还没写回,删了个空)→线程A把旧值写回缓存,变成脏数据永久残留;写后删至少保证在提交之后能把这类竟态产生的脏值再清一次)。项目里这里没有真正"延迟"(commit 后立刻删,不等一段时间),因为读写在同一个 MySQL 主库,不存在主从复制延迟需要等待的场景。

### 3.4 派生缓存的级联失效:反向索引

知文的 Feed 是"整页物化缓存"(一次查询的分页结果整体序列化存一份,不是查询时实时拼装),一篇帖子可能同时出现在多个不同分页的缓存里(不同 size、不同 page、不同小时分片)。要在一篇帖子更新时精确找到所有包含它的分页缓存并清掉,靠的是维护一份**反向索引**(`feed:idx:{postId}:{hour}` → 这个 postId 出现在哪些 pageKey 里,存成 Redis Set),写入分页缓存的同时维护这份索引,失效时先查反向索引再批量删对应的页缓存(`invalidatePublicFeedPagesByPost`)。这是解决"一份数据被物化进多份聚合缓存"场景下如何做精确失效的通用手段,反向索引本身也是缓存(有 TTL),如果反向索引本身已经过期或丢失,对应的页缓存就会失效但清不掉——不过因为页缓存自己也有 TTL,最终还是会自然过期,只是精确失效退化成了"等 TTL"。

`invalidateMineFeedPagesByCreator`(清"我的 Feed"分页缓存)没有对应的反向索引,是用 `SCAN feed:mine:{creatorId}:*` 前缀扫描代替——这是两种不同派生缓存失效手段并存的现状,原因是"我的 Feed"这类按创建者维度缓存的分页数量相对可控,直接扫描的成本可以接受,而公共 Feed(所有用户共享同一批分页)的写入频率和读取规模都大得多,值得为它单独建反向索引。

### 3.5 一个例外:修正式更新而非失效

`knowpost-rpc` 内置的 Kafka listener(`invalidation.go` 的 `patchPublicFeedPagesForCounterEvent`)在处理点赞/收藏计数变化事件时,走的不是"删缓存"而是"就地修正"——尝试重新拼一份包含最新计数的分页内容,直接覆盖 Redis 里的页缓存和 L1(`refreshPublicFeedPageCaches`),只有在拼不出来(比如缓存里的分片数据本身已经缺失)时才回退成删除(`invalidatePublicFeedPageByKey`)。

这是本项目里唯一的 write-through 式做法,原因是点赞计数变化的频率远高于知文内容本身的变化频率,如果每次点赞都直接删掉整页 Feed 缓存,热门内容所在的分页会被频繁击穿回源,代价太高;而"修正"只需要重新读一次已经缓存的分片数据(不需要重新查 MySQL 拼装),成本低很多。这里的一致性代价是:如果 `refreshPublicFeedPageCaches` 内部任何一步失败(比如某个 item 的分片缓存缺失、反序列化失败),它会直接 `return false` 让调用方回退到删除,不会留下"部分字段更新、部分字段还是旧值"的中间态——设计上保证了失败要么完全生效要么完全不生效(整页替换,不是逐字段更新),避免了修正式更新最怕出现的"看似成功但局部脏了"的问题。

## 4. Feed/关注领域里独立于 `cachex` 的其它缓存结构

除了上面走 `pkg/cachex` 通用框架的部分,还有几类 Redis 结构是 logic 层直接操作、没有套用三级缓存抽象,但一致性思路是一致的(写时失效/修正,依赖 TTL 兜底):

- **公共 Feed 的 ids/hasMore 分片缓存**(`feed:public:ids:{size}:{hour}:{page}`)和 **item 缓存**(`feed:item:{postId}`):同样是"读时缓存、写时失效"模式,由 `invalidateKnowPostCaches`/`patchPublicFeedPagesForCounterEvent` 统一维护。
- **关注关系的双向 ZSet**(`uf:flws:{userId}`/`uf:fans:{userId}`,`services/relation/shared/zset`):这类缓存的一致性模型与前面不同,是**异步最终一致**而不是"同请求内尽力同步"——`Follow`/`Unfollow` RPC 本身完全不碰这两个 ZSet,只写 MySQL 的 `following` 表 + `outbox` 事件,ZSet 是 `relation-syncer` 消费 Kafka 事件后才异步补写的。也就是说,`following` 表(MySQL)与 ZSet 缓存之间存在一个**从关注操作提交到 Kafka 事件被消费完成**的正常延迟窗口,这个窗口通常在毫秒到秒级,但如果 Kafka 或 syncer 出现故障会被拉长(参考 `docs/reliability-mq-cache.md` 里对这条链路可靠性的讨论)。这是一个比"写请求内双删"更弱的一致性保证,项目愿意接受它是因为关注列表展示本身对"绝对实时"没有那么敏感。
- **counter 域的位图/SDS**:这一块严格来说不是"MySQL 的缓存"——因为点赞/收藏这个业务本身就没有 MySQL 落地,Redis 位图是唯一的事实来源,不存在"跟 MySQL 保持一致"的问题;SDS 计数缓存与位图之间的一致性靠 `counter-reconciler` 定期对账(见 `docs/counter-reconciler.md`),不是本文讨论的"缓存 vs MySQL"范畴,但经常被放在一起讨论,这里特别指出这一类跟前面几类在本质上是不同的问题。

## 5. 总结:这套体系提供的一致性等级

- **对模型级缓存和详情/分页类应用缓存**:提供的是"**尽力而为的读己之写 + 有界最终一致**"——正常路径下,同一个写请求完成后立刻发起的读请求几乎总能读到最新值(因为失效发生在事务提交之后、响应返回之前的同一次调用链路里);异常路径下(失效动作本身失败),不一致窗口的上界就是各缓存的 TTL(`BaseTTL`/`NullTTL`,以及模型缓存的 `CacheConf` 过期时间),不会无限期不一致。
- **对通过 Kafka 异步链路更新的缓存(如关注 ZSet)**:提供的是更松的最终一致性,一致性窗口不是 TTL 决定的,是"事件产生到被消费完成"的处理延迟决定的,正常情况下很短,故障情况下没有硬上限(取决于故障恢复时间),需要配合可靠性设计(重试、去重、必要时的补偿脚本)一起看。
- **全局都不提供**:强一致(不保证写后所有并发读立刻可见)、跨缓存层的原子性(不存在"MySQL和Redis在同一个事务里提交"这种机制,任何一步失败都只能靠"下一步重试或TTL兜底"收敛,不能回滚)。这个取舍是合理的——用短暂、有界的不一致换取写路径不被缓存一致性协议拖慢,对于知文内容、Feed列表、关注关系这类读多写少且对"绝对实时"容忍度较高的业务场景是恰当的设计;如果项目里出现对强一致性有硬需求的场景(比如涉及金额的计数),现在这套机制是不够的,需要引入其它机制(如版本号乐观锁校验、或者干脆不缓存直接读库)。
