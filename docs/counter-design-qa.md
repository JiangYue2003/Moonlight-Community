# Counter 计数模块设计问答

本文档汇总关于计数(点赞/收藏等)模块架构设计的五个问题,基于 `services/counter`、`pkg/counterlua`、`services/counter/shared/schema`、`services/counter/shared/sds` 等实际代码整理。

## 1. 为什么要单独将计数模块抽离出来?有什么好处?

`services/counter` 是一个独立的领域服务(rpc + api + aggregator + reconciler 四个子进程),而不是把点赞/收藏字段直接塞进 `know_posts` 表里加一列 `like_count`。原因是点赞/收藏这类计数和"知文内容"本质上是两种截然不同的负载特征:

- **读写比和并发量不对等**:一篇知文的标题/正文一天可能改不了几次,但热门内容的点赞可能是秒级几十上百次并发写。如果计数字段和内容字段挤在同一行,每次点赞都要 `UPDATE know_posts SET like_count=like_count+1`,会跟内容更新竞争同一行的锁,而且 MySQL 行锁在高并发自增场景下是明显瓶颈(这也是为什么最终这里完全脱离了 MySQL,纯 Redis 化)。
- **一致性要求不同**:知文的标题改错了是要精确的,点赞数差个一两个,用户完全无感,允许短暂不精确。把两种不同一致性要求的数据分开存,才能给"计数"这类数据用更激进的性能优化手段(位图、批量聚合、最终一致对账),而不用担心拖累"内容"这类需要强一致的数据。
- **可以独立扩容和独立故障隔离**:点赞暴涨(比如内容突然爆火)只会压垂 counter 服务,不会拖慢 knowpost-rpc 或者拖慢发布知文的能力。反过来,knowpost-rpc 抖动也不影响点赞正常写入(位图操作直接打 Redis,不依赖 knowpost-rpc 在线)。
- **复用性**:抽出来后,不只是知文点赞,收藏、关注数、粉丝数(`UserCounter`)都能复用同一套 SDS/位图/聚合/对账的基础设施(`services/counter/shared/schema/user_keys.go` 明确写了"与实体计数共用 SchemaLen/FieldSize"),不用给每个"数字要计数"的场景各自发明一套存储方案。

代码里也留了痕迹能看出这是从既有 Java 系统迁移过来的现成设计(注释"与原 Java UserCounterServiceImpl 的字段编号严格对齐"),说明这套抽离思路是已经被验证过、值得延续的架构决策。

## 2. 为什么选择 Redis 作为底层存储系统?有什么优势?可靠吗?

### 为什么选 Redis

- **原子自增/位操作是 Redis 原生能力**:`SETBIT`/`GETBIT`/`BITCOUNT`/`HINCRBY` 都是 O(1)或近似 O(1)的原子操作,不需要应用层加锁就能保证并发安全,比 MySQL 的行锁自增快一到两个数量级。
- **位图对"去重计数"是天然契合的数据结构**:点赞本质是"某用户对某实体的一个布尔状态",用一个 bit 表示,`BITCOUNT` 直接给出总数,而且同一个用户重复点赞多少次,bit 最终还是 0/1,天然幂等,不需要在应用层做"这个人是否已经点过"的判断查询。
- **内存数据库的吞吐对高频写入更友好**:计数写入是这个系统里 QPS 最高的操作之一,Redis 单机可以轻松扛到几万到几十万 QPS,MySQL 做同等量级的行级自增写入代价高得多。

### 可靠吗(假设生产环境已具备高可用部署:Redis 主从/Cluster + Kafka 多 broker)

可靠性要分三层看:

**存储介质层(Redis 自身)**:主从架构下,位图/SDS 数据在主节点写入后异步复制到从节点。主节点故障时,Sentinel 集群投票选出新主,`go-redis` 的 Failover Client 自动感知切换,应用代码不需要改连接地址,解决的是"单点故障不丢服务"。但 Redis 主从复制默认是**异步**的——主节点故障那一瞬间,如果有还没同步到从节点的写入(复制延迟窗口内的数据),故障切换后这部分写入会丢失。这是主从架构本身的固有物理限制,不是这套 counter 设计的缺陷。好在这些丢失的写入本身也经过 Kafka 那条链路,只要 Kafka 侧消息还在(多副本+`acks=all`保证),影响范围被限制在"切换窗口期内少量点赞"这个很小的量级。Redis Cluster 下每个分片本身也配从节点,单分片主节点故障只影响该分片对应的 slot,不是全局不可用,连带影响面比单主从更小。

**中间处理链路层(Kafka + aggregator)**:即使 Kafka 多副本部署,消息传递语义依然是"at-least-once",不是"exactly-once"。`counter-aggregator` 的聚合折算逻辑(`incr_field.lua`+`decr_field.lua`分两步、失败可重放)和消费端的 SETNX 去重共同保证这一层的可靠性不依赖任何单点组件,即使 Kafka 集群短暂全体不可用,恢复后会继续消费未处理完的 offset,不会永久丢事件。

**事实层的自我修复能力(reconciler)**:这是这套设计最关键的可靠性保障,且不依赖任何基础设施的高可用程度——`counter-reconciler` 定期用位图重新计算真值,校正 SDS 的偏差。哪怕前两层都做到生产级高可用,消息丢失/顺序错乱这类问题在分布式系统里永远无法完全消除为零概率事件,reconciler 保证了"即使发生了小概率的丢失,系统会在下一个对账周期内自动收敛回正确值"——基础设施高可用降低故障概率,reconciler 兜底"故障已经发生之后如何恢复正确性",两者互补而非替代。

**结论**:三层防护(存储介质容错、消息传递容错、定期对账自愈)叠加后,能把"点赞数据永久性错误"的概率压得非常低。唯一无法通过基础设施高可用完全消除的,是主从复制异步窗口期内那一小段"故障瞬间尚未复制的写入"理论上仍可能丢失——这是所有基于异步复制的存储方案的通用物理限制,是分布式系统 CAP 权衡下的必然代价,可以通过缩小复制延迟、增加同步确认副本数等手段进一步降低概率,但无法做到数学上的绝对为零。

## 3. Redis 存储计数的实现细节

整体是三层结构接力,各自负责不同职责:

**位图层(事实层)**:`bm:{metric}:{etype}:{eid}:{chunk}`,比如 `bm:like:knowpost:331127866555371520:0`。每个用户对该实体的点赞状态占一个 bit,`BitOf(userId)` 决定这个用户落在哪个 bit 位置。写入靠 `toggle.lua` 一次 `GETBIT`+条件 `SETBIT`,返回值区分"真的变化"(1)和"幂等无操作"(0),调用方只在真变化时才继续往下发 Kafka 事件——这一步保证了整条链路"位图永远是唯一权威的原始记录"。

**聚合桶层(过渡缓冲)**:`agg:v1:{etype}:{eid}`,一个 Redis Hash,字段是 SDS 里的字段下标(字符串形式的 `idx`),值是尚未落盘的累计 delta。`counter-aggregator` 消费 Kafka `counter-events` 后直接 `HIncrBy` 到这里——这一步只是数字累加,不管顺序,也不去重(依赖 Kafka 层和业务层的幂等保证不会有重复的 delta 混进来)。

**SDS 读取层(对外服务)**:`cnt:v1:{etype}:{eid}`,一段固定长度字节串(见问题4)。`RunFlusher` 定时扫聚合桶,对每个字段调 `incr_field.lua` 把 delta 折算进 SDS,再调 `decr_field.lua` 把已经折算掉的部分从聚合桶扣掉(`HINCRBY -delta`,如果扣到0就 `HDEL` 整个字段)。这两步分开是为了保证"折算进SDS"和"从聚合桶清除"任一步失败,下次重试时能拿到正确的剩余量重新算,不会因为中途失败导致同一份 delta 被算两次或漏算。

读的时候(`GetCounts`/`IsMarked`)分两条路:`IsMarked` 直接 `GETBIT` 查位图(要精确知道"这个用户点没点过"必须查事实层,SDS 里没有单用户维度信息);`GetCounts` 直接 `GET` SDS 整段字节串然后按下标解出对应字段,不查位图(位图是全量扫描+`BITCOUNT`求和,代价远高于直接读一个固定长度的字节串,只有对账时才会去扫位图求真值)。

## 4. SDS 是什么?为什么用固定结构字节串,不用 Hash 存多个字段?

SDS 在这里是"固定长度、多字段打包进同一个字符串"的自定义二进制编码——`cnt:v1:{etype}:{eid}` 这个 key 的值是一段 `SchemaLen(5) * FieldSize(4) = 20` 字节的字符串,每 4 字节是一个大端编码的 int32 字段(read/like/fav/comment/repost),用固定偏移量 `idx*4` 定位某个字段,不带任何字段名或分隔符。名字大概是借用 Redis 底层字符串类型 SDS(Simple Dynamic String)的概念,强调它是"用普通字符串结构编码出的结构体",不是 Redis Hash 那种原生多字段类型。

为什么不用 Hash(比如 `HSET cnt:{eid} like 100 fav 20`),而要自己拿字符串编码搞一套二进制协议:

- **内存开销**:Redis Hash 底层小对象用 `listpack`/`ziplist`,每个字段除了值本身,还要存字段名字符串("like"/"fav"这些)、以及 Hash 结构自身的元数据开销。而固定字节串完全没有字段名,5 个字段总共就 20 字节,数据量放大到几百万/千万级实体时,内存差距是数量级的——这本来就是一个高频访问、体量巨大的计数存储场景,内存效率是第一优先级考量。
- **单次 GET/SET 就是整行操作,减少往返和命令复杂度**:一次 `GET` 拿到全部 5 个字段,不需要 `HGETALL`/`HMGET` 这类多字段命令,协议解析也更简单(客户端直接按偏移量切片解码,不需要处理 Redis Hash 返回的 field-value 交替数组)。
- **原子多字段操作用 Lua 脚本比 Hash 天然支持得更灵活**:这套设计里"折算并归零/裁剪到无符号32位边界"(`incr_field.lua` 里有 `val<0` 归零、`val>4294967295` 封顶 的逐字段边界处理)这类定制逻辑,写成对固定字节串的操作和写成对 Hash 字段的操作,复杂度是一样的,但字节串省内存的优势是 Hash 拿不到的。
- **和用户维度计数(`ucnt:{userId}`)共用同一套编码/脚本**:`schema/user_keys.go` 明确写了"SchemaLen/FieldSize 与实体计数共用,因此 incr_field.lua 可被两套 SDS 共用"——如果用 Hash,字段名在不同场景下还是要各自定义(followings/followers/posts vs like/fav),脚本层不能真正做到通用;而固定字节偏移量的方案,只要"第几个字段"这个下标语义定义好,同一套 Lua 脚本可以无差别套用在任意一种实体上。

代价也很明确:可读性差(Redis CLI 里直接 `GET` 出来是一段乱码,不像 Hash 那样能直接看到字段名和值),扩展字段需要提前预留位置(代码里已经预留了 `read`/`comment`/`repost` 三个目前不用的下标,用预留下标而不是"改变长度"来应对未来扩展,避免旧数据和新 schema 不兼容)。

## 5. 为什么要位图分片?分片大小怎么选?

`BitmapKey(metric, etype, eid, chunk)` 里的 `chunk = ChunkOf(userId) = userId / ChunkSize`,`ChunkSize = 32768`(32768 位 = 4KB)。也就是说同一个实体的点赞位图不是一个无限增长的大 key,而是按用户 ID 每 32768 个一组切成多个独立的 4KB 分片 key。

**为什么要分片,不用一个无限大的位图**:

- **避免超大 key 的性能和运维风险**:Redis 的 String(位图底层就是 String)理论上限是 512MB,如果用户基数达到十亿级,一个不分片的位图 key 可能长到几百 MB。超大 key 会带来几个具体问题:`BITCOUNT`/`GETBIT`/`SETBIT` 这些操作本身复杂度会变高(尤其 `BITCOUNT` 是要扫描整个字符串),而且 Redis 是单线程处理命令,操作一个几百MB的大 key 会长时间占用主线程,阻塞其它请求(经典的 Redis"大key"问题);再加上 Redis Cluster 模式下,单个 key 不能跨节点分片,一个巨大的 key 会让某个节点的内存分布严重不均衡。
- **分片后可以并行/独立操作**:`scanBitmapTotal`(对账时统计真实总数)用 `SCAN bm:{metric}:{etype}:{eid}:*` 找出该实体所有分片,再用 Pipeline 批量对每个分片单独 `BITCOUNT` 后求和——分片让这个"总数统计"操作可以拆成多个小操作并行执行(pipeline批量发送),而不是一次性对一个巨大位图做单次昂贵的 `BITCOUNT`。
- **减少稀疏浪费**:大部分实体(冷门内容)的点赞用户数远小于总用户数,如果按最大用户ID分配位图长度,大量位图会是几乎全零的稀疏数据,浪费内存(虽然 Redis 位图对全零区域有一定的稀疏存储优化,但仍不如按需分片来得干净)。分片后,一个冷门实体大概率只会用到第 0 个分片(用户ID小的活跃早期用户),后面的分片 key 根本不会被创建,天然按需增长。

**分片大小(32768位=4KB)怎么选**:这是一个典型的"分片粒度换查询成本"的折中——分片越大,单实体的分片数越少,`scanBitmapTotal` 需要扫描和 `BITCOUNT` 的 key 数量越少(减少对账/统计时的 Redis 命令数和网络往返);分片越小,单个 key 的体积越小,越不容易碰到大key问题,但分片数量会显著增多,SCAN 遍历和 Pipeline 批量执行的开销会上升。4KB 这个尺寸本身是一个相当保守、远低于 Redis 大key警戒线(通常建议单 key 不超过 10KB~1MB 视场景)的取值,32768 位也刚好能被常见的用户ID范围整除成一个可控的分片数量(比如百万级用户,分片数量大概是几十个,对 SCAN 和 pipeline 而言完全是轻量级操作)。这个数值本身没有一个数学上唯一正确的"最优解",更像是"经验上足够安全、又不至于分片数量爆炸"的工程选择,和 Redis 官方文档里对大 key 阈值的建议量级是一致的。
