# 前后端协同说明（zhiguang_fe-main）

本文基于前端实际代码调用行为整理，目标是让后端按“前端真实消费方式”完成接口对齐。

## 1. 全局协同约定

1. 前端统一通过 `apiFetch` 发请求。
2. 开发环境默认走 Vite 代理：`/api` -> `http://localhost:8080`。
3. 默认 `Content-Type: application/json`；上传头像用 `FormData`，不主动设置 JSON 头。
4. 默认携带 `credentials: include`，后端若有 Cookie/CSRF 策略需兼容。
5. 非 `GET/HEAD/OPTIONS` 请求时，前端会尝试从 Cookie 读取 `XSRF-TOKEN` 并附加 `X-XSRF-TOKEN` 头。
6. 鉴权头规则：
   1. 未显式传 `accessToken` 时，前端从 `localStorage.zhiguang_auth_tokens` 读取并附加 `Authorization: Bearer <token>`。
   2. 显式传 `accessToken: null` 时，强制不带 Authorization（用于 refresh）。
7. 错误处理规则：前端优先展示响应 JSON 中的 `message` 字段；无 JSON 时展示响应文本。
8. `204 No Content` 会被前端识别为 `void` 成功。

| `authService.sendCode` | `POST /api/v1/auth/send-code` | body: `{ scene, identifierType, identifier }` | `{ identifier, scene, expireSeconds }` |

## 3. 复杂链路协同（重点）

## 3.1 知文发布链路（CreatePage）

前端动作顺序：
1. `createDraft` 获取 `postId`。
2. 正文转 `File(content.md)`，计算 `sha256`。
3. 调用 `presign(scene=knowpost_content)` 获取 `putUrl/objectKey/headers`。
4. `PUT putUrl` 上传正文，读取响应头 `ETag`。
5. `confirmContent` 上报 `{ objectKey, etag, size, sha256 }`。
6. `update` 提交元数据（标题、标签、图片列表、可见性、摘要等）。
7. `publish` 完成发布。

后端协同要求：
1. `id` 必须可被前端当字符串稳定处理。
2. `presign.headers` 必须原样可用于 `PUT`。
3. OSS/COS/S3 侧必须允许前端读取 `ETag` 响应头（CORS `Expose-Headers`）。
4. `confirmContent` 支持 `etag` 带双引号。
5. `update` 支持部分字段更新，缺失字段不应被清空。

## 3.2 图片上传链路（CreatePage）

1. 最多 15 张，前端逐张上传。
2. 每张图片调用一次 `presign(scene=knowpost_image)`。
3. 上传成功后前端用 `putUrl.split("?")[0]` 作为展示 URL 写入 `imgUrls`。

后端协同风险点：
1. 若对象存储私有读，`putUrl` 去 query 后可能不可访问；需确认是否有公网读域名策略。
2. 若最终展示 URL 不等于 `putUrl` 去 query，建议后端返回可展示 URL 字段供前端使用。

## 3.3 SSE 流式问答链路（CourseDetailPage）

请求：
1. `GET /api/v1/knowposts/{id}/qa/stream?question=...&topK=5&maxTokens=1024`
2. 前端使用 `EventSource`，不带 Authorization 自定义头。

前端状态行为：
1. 点击发送：清空旧答案，关闭旧连接，创建新连接。
2. `onmessage`：将 `e.data` 追加到 `ragAnswer`，实时渲染 Markdown。
3. `onerror`：前端关闭连接并停止 loading，不弹默认异常文案。
4. 点击停止或页面卸载：主动 `close()`。

后端协同要求：
1. 返回 `Content-Type: text/event-stream`，建议 `Cache-Control: no-cache`。
2. 发送格式需符合 SSE 规范（`data: ...\n\n`）。
3. 对非公开内容返回明确错误（当前前端限制仅公开可问答）。
4. 异常中断时允许前端无害关闭，不依赖额外结束帧。

## 4. 鉴权与会话协同（AuthContext）

1. 前端每 60 秒触发一次 `refresh` 检查。
2. 当 `Date.now() >= expiresAt - 5000ms` 时，调用 `/token/refresh`。
3. refresh 成功后，前端会立刻调用 `/auth/me` 刷新用户资料。
4. refresh 失败会触发前端本地登出清理。

后端协同建议：
1. `/token/refresh` 不依赖旧 access token。
2. `/auth/me` 响应字段尽量稳定，避免登录态闪断。
3. 错误响应统一含 `message`，便于前端直接透传展示。

## 5. 已识别的不一致与待对齐项

1. 字段命名不一致风险：
   1. 个人资料更新请求用 `zgId`。
   2. 认证用户信息里前端同时读取 `zhId`（编辑页预填也用 `zhId`）。
   3. 建议后端统一字段名并提供兼容期映射。
2. 头像字段历史兼容：
   1. 前端列表读取 `authorAvatar`，兼容 `authorAvator` 拼写。
   2. 建议后端固定输出 `authorAvatar`。
3. 关系计数语义待统一：
   1. 页面文案显示“获赞/获藏”。
   2. 字段名是 `likedPosts/favedPosts`，可能被理解为“我点赞/我收藏数量”。
4. 详情作者 ID 来源：
   1. 前端优先用 `authorId`。
   2. 若缺失，尝试从头像 URL 正则推断，可靠性低。
   3. 建议后端稳定返回 `authorId`。
5. 正文读取跨域：
   1. 前端直接 `fetch(contentUrl, { credentials: "omit" })` 拉文本。
   2. 需后端或对象存储保证跨域可读与文本可访问。

## 6. 后端联调最小验收清单

1. 认证：验证码登录、注册自动登录、refresh、logout 全流程打通。
2. 资料：头像上传与资料更新后，`/auth/me` 可立即看到新值。
3. 发布：草稿 -> 预签名 -> 上传 -> 确认 -> 更新 -> 发布全链路成功。
4. 展示：`feed/mine/detail` 字段完整，点赞收藏初始状态正确。
5. 交互：点赞/收藏/关注/取消关注行为与计数变更一致。
6. 搜索：关键词检索与联想建议均可用，分页 `after` 正常推进。
7. SSE：问答可流式返回，前端可中途停止，无资源泄漏。
