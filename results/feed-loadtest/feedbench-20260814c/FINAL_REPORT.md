## 1. 结论先行

### 1.1 当前单机最大承载能力

“最大承载能力”必须按操作拆开描述，不能把读 QPS 和完整发布 QPS 合成一个数字：

| Hybrid 路径 | 建议作为容量基线的档位 | 成功吞吐 | P95 | 已观测边界 |
|---|---:|---:|---:|---|
| RPC 分散首页读取 | c128 | 1,592.80 QPS | 101.03 ms | c256 仍为 0 失败，但吞吐仅增 0.4%、P95 升至 193.74 ms |
| RPC 热点首页读取 | c128 | 1,536.62 QPS | 103.20 ms | c256 吞吐下降至 1,514.78 QPS、P95 升至 201.64 ms |
| RPC 深分页 | c128 | 1,173.70 QPS | 136.21 ms | c256 吞吐下降至 1,150.92 QPS、P95 升至 276.74 ms |
| Gateway 分散首页读取 | c32 | 953.19 QPS | 42.97 ms | c128 吞吐下降至 869.06 QPS、P95 升至 180.42 ms |
| Gateway 热点首页读取 | c32 | 986.51 QPS | 41.43 ms | c128 为 1,005.29 QPS，但 P95 升至 160.61 ms |
| RPC 完整发布工作流 | c32 | 10.09 次发布/秒 | 3,242.93 ms | 拐点 c36；无错误上界 c40；c44 首次出现错误 |
| Gateway 完整发布工作流 | c32 | 10.01 次发布/秒 | 3,240.69 ms | c128 全部失败，未对 32～128 做细粒度补测 |

因此，当前环境下 Hybrid 最适合对外表述为：

- 读取稳定容量约为 RPC 1.5k～1.6k QPS，Gateway 约 0.95k～1.0k QPS。
- 端到端完整发布稳定容量约为 10 次/秒，稳定并发为 32。
- Hybrid 发布性能拐点为 c36；c40 仍可全成功但已经不是经济运行点；c44 触发公共发布链路熔断。
- 读取在测试最高档 c256 仍然没有失败，所以 1.6k QPS 是本轮“观测峰值/稳定曲线”，不是已经打穿后的绝对上限。

### 1.2 三种策略的最终取舍

| 策略 | 读取表现 | 发布与资源成本 | 适用结论 |
|---|---|---|---|
| Push | 最强；RPC 分散读 c128 达 2,759.77 QPS / P95 60.04 ms | 发布后异步 fanout；c32 发布时 Kafka lag 峰值 32、Redis 峰值 28,000 ops/s，三者最高 | 以写放大和异步一致性换取最好的读性能；大 V 会显著放大粉丝 Inbox 写入 |
| Pull | 最弱；RPC 分散读 c128 为 585.63 QPS / P95 243.79 ms | 发布不产生 fanout lag；c32 Redis 峰值 13,214 ops/s，三者最低 | 写路径轻，但每次读都要归并所关注作者的 Outbox，关注数增大后读放大明显 |
| Hybrid | 居中；RPC 分散读 c128 为 1,592.80 QPS / P95 101.03 ms | 普通作者推、大 V 拉；c32 Redis 峰值 16,927 ops/s；更高发布并发出现可控 Kafka lag | 避免大 V 扇出风暴，同时保留普通作者 Inbox 快读；不是单项冠军，但风险最均衡，建议继续作为默认策略 |

在同一 c128 分散读负载下，Push 吞吐约为 Hybrid 的 1.73 倍，Hybrid 约为 Pull 的 2.72 倍。Hybrid 的意义不是取两者平均值，而是把最危险的大 V 写扩散转移到读时归并，同时保留普通作者的推模式收益。

### 1.3 SLA 在本报告中的含义

SLA（Service Level Agreement）是对可用性、延迟、错误率等服务水平的正式承诺，通常还带有统计周期和违约责任。工程内部更常用 SLO 表达目标，例如“月度可用性 99.9%”或“P95 小于 200 ms”。

本轮没有把任意 SLA/SLO 数值设成硬门槛。P95、P99、错误率用于帮助选择容量余量；压测是否有效取决于请求结果、性能曲线、资源指标和正确性验证是否完整，而不是是否碰到某条人为参考线。

## 3. 正确性与冒烟验证

三种策略均通过可重复、机器可读的独立冒烟。每轮同时验证读者与两类作者可见性、Feed 无重复、manifest 范围 Inbox 精确命中数、两类 Outbox、Kafka log-end 增量和最终 lag：

- Push：普通作者和大 V 都产生 fanout，分别验证 100/100 与 1,100/1,100 粉丝 Inbox 写入，最终 Kafka lag 为 0。
- Pull：两类作者都写 Outbox，不增加 fanout offset，阅读者可以看到两类新帖。
- Hybrid：普通作者进入 Inbox fanout，大 V 进入 Outbox，阅读结果同时包含两类内容。
- 证据文件：`smoke-push.json`、`smoke-pull.json`、`smoke-hybrid.json`；三份均为 `complete: true`。
- 每轮施压前执行 run-id/manifest 范围内的 Feed Redis key 精确重置，未扫描或删除无归属业务 key。
- 正式矩阵结束后所有核心容器保持健康、restart count 为 0；KnowPost 已恢复为 `FEED_STRATEGY=hybrid`。
- 收口阶段额外保存 `environment-snapshot.json`：Gateway、KnowPost、Relation、Counter 均为 running/healthy、restart count=0，Kafka offset 为 2,954/2,954、lag=0。

冒烟过程中发现并修复了一处真实问题：最初强制策略只作用于写入器，读取器仍按 1,000 粉丝阈值分类，导致强制 Pull 下普通作者 Outbox 内容不可见。现在 FeedReader 与 FeedWriter 注入同一策略，并增加三策略回归测试。

## 5. 发布结果与瓶颈定位

### 5.1 c32 完整发布

| 策略 | 成功 | QPS | P95 | Kafka lag 峰值 | KnowPost CPU 峰值 | Redis ops/s 峰值 | MySQL running 峰值 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Push | 128/128 | 11.38 | 2,985.75 ms | 32 | 150.63% | 28,000 | 6 |
| Pull | 128/128 | 10.76 | 3,029.48 ms | 0 | 145.52% | 13,214 | 4 |
| Hybrid | 128/128 | 10.09 | 3,242.93 ms | 0（1 秒采样未捕获） | 147.16% | 16,927 | 3 |

Push 的客户端发布请求只负责把 fanout 事件交给 Kafka，真正的粉丝 Inbox 扇出在后台消费，因此 11.38 QPS 不能理解为所有粉丝 Inbox 已同步写完。Kafka lag 和 Redis ops/s 揭示了被延后的写放大；编排器会等 lag 清零后才进入下一场景。

Hybrid 在更细边界测试中得到：

| 并发 | 成功 | QPS | P95 | Kafka lag 峰值 | 判断 |
|---:|---:|---:|---:|---:|---|
| c32 | 128/128 | 10.09 | 3,242.93 ms | 0 | 峰值无错误吞吐、稳定档 |
| c36 | 144/144 | 9.51 | 3,879.47 ms | 31 | 吞吐下降且延迟上升，性能拐点 |
| c40 | 160/160 | 9.47 | 4,299.72 ms | 35 | 仍全成功，但已进入高延迟区 |
| c44 | 34/176 | 8.51 | 3,861.26 ms（仅成功样本） | 0 | 142 次 circuit breaker，首个错误档 |

在 40 秒 c128 读负载之后重新施加 Hybrid c32 完整发布，仍为 128/128、10.13 次/秒、P95 3,310.40 ms，进一步支持 Hybrid c32 的稳定档判断。相同顺序下 Push 仅 22/128、Pull 127/128，说明“空闲/新进程纯发布容量”和“持续读后的写突发容量”不能混为一谈。

### 5.2 失败根因不是单一 Feed 策略

c44 的 142 次失败全部发生在 `publish_metadata`，错误被明确分类为 `circuit_breaker`；已经进入最终 `publish_commit` 的 34 次全部成功。主矩阵 c128 时三种策略也都在 Metadata 阶段大面积失败：Push 3/512、Pull 2/512、Hybrid 1/512。

这表明纯发布硬边界首先由共享的 Metadata/缓存失效熔断链路决定，而不是由 Push、Pull 或 Hybrid 的 Feed 路由直接决定。c128 主矩阵在错误分类增强前执行，报告中显示为 `request_error`；结合完全相同的失败阶段以及 c44 的可重复结果，可以合理推断为同一类缓存熔断，但该部分属于证据支持的推断。

风险点是：数据库更新成功后若缓存失效返回熔断错误，客户端会认为操作失败并重试，可能形成“数据已变更、工作流未继续”的部分成功。后续应优先梳理 Metadata 幂等、缓存删除失败的降级语义和补偿机制，再考虑单纯提高 breaker 阈值。

## 6. 混合负载

90/10 场景在 RPC c256 下三种策略均无错误。更重的 80/20 场景显示出真正的策略差异：

| 并发 | 策略 | Read 成功/QPS/P95 | Publish 成功/QPS/P95 |
|---:|---|---:|---:|
| c128 | Push | 240/240；1,552.23；97.92 ms | 60/60；10.11；2,471.32 ms |
| c128 | Hybrid | 240/240；942.32；129.21 ms | 60/60；9.43；2,839.02 ms |
| c128 | Pull | 240/240；426.61；300.06 ms | 60/60；9.49；2,879.12 ms |
| c256 | Push | 240/240；1,563.70；135.33 ms | 60/60；10.39；4,883.73 ms |
| c256 | Hybrid | 240/240；989.05；208.42 ms | 1/60；0.17；883.74 ms（成功样本） |
| c256 | Pull | 240/240；445.39；457.64 ms | 1/60；0.17；837.85 ms（成功样本） |

c256 时 Hybrid/Pull 的失败集中在最终 Publish/Outbox 相关阶段，而 Push 仍保持 60/60。这个现象与“Pull 路径在发布请求内同步写 Outbox、Push 路径异步 fanout”的设计差异一致，但原始报告只保存了 `request_error`，没有保存 Redis pool 等待、Outbox 命令耗时或对应服务端日志关联，因此只能作为待验证假设，不能直接写成已证明根因。

Gateway 的两种混合比例在 c1、c32、c128 均全成功。80/20、c128 下读吞吐/P95 分别为 Push 1,066.94/135.65 ms、Hybrid 706.16/176.27 ms、Pull 332.60/364.52 ms；Gateway 入口下仍保持 Push > Hybrid > Pull 的吞吐与尾延迟梯度。

三种策略均在容器重启、精确 reset、自动 smoke、125 条种子帖之后执行 c128 突发读和 30 秒稳态分散读：

| 策略 | c128 突发读 QPS / P95 / 成功 | c128 30 秒稳态 QPS / P95 / 成功 |
|---|---:|---:|
| Push | 2,695.27 / 62.44 ms / 27,020/27,020 | 2,744.23 / 61.07 ms / 82,405/82,405 |
| Hybrid | 1,544.12 / 106.30 ms / 15,526/15,526 | 1,590.01 / 103.53 ms / 47,777/47,777 |
| Pull | 620.17 / 265.13 ms / 6,291/6,291 | 670.94 / 232.16 ms / 20,193/20,193 |

30 秒结果与主矩阵 c128 的数量级和排序一致，三策略均无读错误；它降低了“3 秒窗口偶然峰值”的风险，但仍不等于 30 分钟以上的生产稳态证明。

紧接 40 秒读负载后的 c32 完整发布突发：

| 策略 | 成功 | QPS | P95（成功样本） | 首次 Kafka drain 复核 | 最终 lag |
|---|---:|---:|---:|---:|---:|
| Push | 22/128 | 8.95 | 2,336.12 ms | 1.157 s | 0 |
| Pull | 127/128 | 10.54 | 3,081.57 ms | 1.078 s | 0 |
| Hybrid | 128/128 | 10.13 | 3,310.40 ms | 1.139 s | 0 |

Push 的 106 次和 Pull 的 1 次失败都发生在 Metadata 阶段并明确分类为 `circuit_breaker`；Hybrid 本轮全成功。drain 数字包含一次 Docker/Kafka CLI 采集耗时，应理解为“约 1.2 秒内首次观测到 lag=0”，不是毫秒级精确消费耗时。

没有执行破坏性“冷 Feed 缓存清理”：当前 Inbox/Outbox 是个性化 Feed 的物化主状态，并不存在删除后可无损从 DB 自动重建的同义缓存层。直接清除会测试数据丢失路径，而不是普通冷缓存回源；真正的冷启动测试应先设计可重建边界或仅隔离详情 L1/L2。

## 8. 测试中完成的工程改进

- FeedWriter/FeedReader 支持 `push`、`pull`、`hybrid` 强制策略，默认仍为 Hybrid，非法配置启动失败。
- 修复强制策略只影响写、不影响读的可见性缺陷，并加入回归测试。
- Gateway 新增鉴权 Following Feed 接口；客户端不能通过 query 参数伪造其他用户。
- Gateway 发布压测实现真实 Draft、Metadata、Confirm、Publish HTTP 全链路。
- 压测工具支持固定请求数/固定时长、真实 P50/P90/P95/P99、错误分类、双入口、精确 Feed key 重置、资源监控与结构化报告。
- 新增可复现数据 manifest、策略切换编排器、Kafka drain 轮询和失败时自动恢复 Hybrid。
- 一键矩阵现已包含 Hybrid c36～c96 发布边界，以及每种策略的 10 秒 burst read、30 秒 steady read、读后 burst publish 与恢复观测，不再依赖人工补测命令。
- 新增 `compare` 阶段，自动输出 JSON、CSV、Markdown 三策略容量汇总。
- 固定 seed 改为按 `(seed, request ordinal)` 无状态选取目标，避免 worker 调度改变读者/作者分布；运行前校验容器实际策略，拒绝错标报告。
- `cleanup` 阶段使用 Run ID 二次确认、manifest 全量 ID/email 所有权校验和 MySQL 事务，精确清理用户、关系、帖子、Outbox、登录日志及对应 Redis keys；报告和 manifest 默认保留。
- `cleanup-dry-run` 已在当前数据集完成只读演练：全量验证 1,225 个用户，计划范围为 7,500+7,500 条关系、11,875 篇帖子、17,695 条 Outbox、2,091 条登录日志和 139,185 个可推导 Redis keys；未执行删除。
- 发布/混合场景在停止施压后继续采样，持久化 Kafka drain 与最终 lag。
- 新报告会持久化核心容器 running/healthy/restart count；当前快照明确标记 Prometheus 应用指标和关联 timeout/panic/retry 日志未采集。
- 修复共享应用镜像不可构建的 `alpine:3.23` 标签，改用稳定的 Alpine 3.22，并从 Go 官方下载、校验 amd64/arm64 的 Go 1.25.8 工具链；新 Gateway 镜像已实际构建并通过容器级 HTTP 校验。

## 9. 建议

1. 继续使用 Hybrid 作为默认策略。当前 1,000 粉丝阈值在测试拓扑中正确隔离了普通作者和大 V 风险。
2. 对外容量先按稳定档而不是观测峰值规划，并至少保留 30%～50% 余量；生产值必须在独立压测机和类生产资源限制下重新标定。
3. 优先修复 Metadata/cache invalidation 的部分成功与熔断语义。不要在未完成幂等和补偿设计前只调高 breaker 阈值。
4. 为 Outbox 写入增加更细粒度指标，区分 Redis pool 等待、命令耗时、breaker 状态和作者类型；再决定是否需要连接池、Pipeline 或异步化优化。
5. 将本次补测的恢复记录扩展到每一档正式矩阵，并改用常驻 Kafka Admin 客户端或服务指标，去掉每次 Docker CLI 启动约 1 秒的测量噪声。
6. Gateway 高并发损耗明显，下一轮把鉴权、HTTP JSON、RPC 转发分别打点，避免把网关开销误判为 Feed 合并成本。

## 10. 局限性

- 这是 Windows + Docker Desktop 的共享开发机结果，负载发生器与服务同机；不能直接外推生产集群。
- 核心容器未设置 CPU/内存限额，后台还有 Search、Canal、Elasticsearch 等服务产生环境噪声。
- 主阶梯读窗口为 3 秒，补测加入了 c128 30 秒稳态；仍不足以证明 30 分钟或更长稳态容量，也未覆盖完整 GC 周期和长时间内存增长。
- 三种策略按 Push → Pull → Hybrid 顺序运行；Feed Redis key 每轮精确重置并重新播种，但 MySQL 测试帖子为保留报告而未在策略间删除，深分页候选深度存在顺序性噪声。
- 主矩阵执行时仍使用 worker-local RNG；相同 seed 和并发参数保证统计分布相近，但请求目标序列不是逐 ordinal 完全一致。工具现已改为无状态 ordinal 映射，9 份补测使用新口径；主矩阵没有重跑，因此三策略差异仍包含少量调度噪声。
- Kafka 采用 1 秒资源采样，短暂 lag 可能未被捕获；Hybrid c32 显示 0 不代表绝对没有瞬时积压。
- 主矩阵只确认场景间 Kafka lag 清零，没有持久化每次 drain；9 份补测已保存恢复字段，但约 1 秒 CLI 采集分辨率仍较粗。
- 未执行 30 分钟以上长稳态、网络故障、Redis/MySQL 限流、Kafka 消费者中断和恢复演练；这些应作为生产容量验收的下一阶段。
- 本轮未接入 Prometheus 应用层指标，也未持久化逐请求关联的服务端 timeout/panic/retry 日志；已有 Docker/Kafka/Redis/MySQL 采样和最终容器快照不能替代应用内部可观测性。
- 测试数据当前保留在开发库中，方便复核；可先用 `reset-feed` 只清 Feed Redis 状态，或显式 `cleanup -confirm-cleanup <run-id>` 做全量 manifest 范围清理。Elasticsearch 文档和 Kafka 历史不会被 cleanup 删除。
